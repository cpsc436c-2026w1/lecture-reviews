L12 review: DynamoDB as OLTP storage, distributed database problems and properties

If you need to look up a term, the relevant vocabulary is below.

Which engine fits each workload?

A recap of L11: the rides history in the lakehouse, read by different engines.

--- shuffle_answers: true --- ## For each workload, choose the engine that fits it best. Each option may be used once, more than once, or not at all. - Analysts occasionally ask new questions about trip history data, without idle billing :: Athena > Athena bills per TB of Data scanned and charges nothing between queries, which suits best ad-hoc queries. S3 storage is billed either way. - Nightly job rewrites yesterday's trips into a sorted Iceberg table. It runs for about 10 minutes :: Glue job > A Glue job bills DPU-hours for the run only, so a regular batch pays for its 10 minutes and nothing else. - Dashboard executes the same 20 large-scan queries every few minutes, all day :: Trino on EMR > Calculate the crossover first: at this load the cluster, billed per node-hour, costs less than paying per query (the review page works the numbers). - :: Lambda > With custom layers and the maximum memory setting you might be able to run some of these workloads in Lambda. However, it is not the best solution for any of them.

Which store fits each workload?

Operational and analytical stores side by side: DynamoDB, a relational database, S3 and the lakehouse.

--- shuffle_answers: true --- ## Match each workload to the store that fits it best. Each option may be used once, more than once, or not at all. - A game keeps each player's score as one small record, updated by player id tens of thousands of times a second at peak. Nothing joins it to other data :: DynamoDB > Small items, always found by one key, at a rate that changes with the game: what DynamoDB is built for. - A shopping site reads and writes each visitor's cart by cart id on every page view, with ten times the traffic on sale days. No query joins carts :: DynamoDB > One key per request and traffic that jumps: DynamoDB scales on demand and answers in milliseconds. - An order system runs one query that joins customers, orders and products :: Relational database (RDS) > Joins across tables are what a relational database does. DynamoDB has no joins. - A video site stores each uploaded video, files of several gigabytes :: S3 > A DynamoDB item is at most 400 KB. Large files go to S3, as objects. - Analysts ask a new SQL question every week over 5 TB of order history from three years :: Lakehouse (Athena on Iceberg) > Ad hoc questions that scan a lot of history: columns in Parquet, billed by Data scanned. - A nightly report adds up about 3 TB of sales records by product :: Lakehouse (Athena on Iceberg) > A scan of terabytes on DynamoDB would read every item, for hours and dollars. The lakehouse reads only the columns the report needs.

Which reads need a strong read?

Reads in the trip app: when a read may be a moment old, and when it must return the latest write.

--- shuffle_answers: true --- ## For each read in the trip app, choose the least expensive option that meets its need. Each option may be used once, more than once, or not at all. - The driver app reads trip t-0042 back right after its own accept succeeded, to show the assigned driver :: Strongly consistent read > Read-after-write: an eventual read might come from a replica without the accept and show the trip still "requested". - The driver app shows whether the passenger has cancelled, right after the passenger phoned the driver to say so :: Strongly consistent read > Another user's write the driver already knows about: an eventual read could still show the trip as active. - The passenger app refreshes the driver's position on the map every two seconds, where an old position is acceptable :: Eventually consistent read > An old position is acceptable here, later refreshes replace it, and eventual reads cost half. - The passenger app shows the fare right after the passenger's promo-code update succeeded :: Strongly consistent read > Read-after-write: the passenger just wrote, and an old fare on screen would look like the promo failed. - A list of the passenger's past trips, where a trip that just finished may appear on the next refresh :: Eventually consistent read > An old list is acceptable on this screen, and eventual reads cost half. - :: Federated query from Athena > A query taking seconds through a connector serves reports, not a screen that must open in milliseconds.

Which problem is each situation?

A food-delivery app keeps live orders in DynamoDB and order history in a lakehouse.

--- shuffle_answers: true --- ## Food-delivery app keeps orders in DynamoDB and order history in a lakehouse. Match each situation to the problem it shows. Each option may be used once, more than once, or not at all. - A customer edits the delivery address, and the confirmation screen right after shows the old one :: Replication lag > The read came from a replica that did not have the write yet. A strongly consistent read would have shown it. - Two couriers both mark the same order "picked up", and the order ends up with the second courier's name :: Lost update > Both read "waiting" correctly. The second write replaced the first. A conditional write would have refused one. - A nightly load into the lakehouse runs twice after a timeout, and yesterday's orders appear twice :: Non-idempotent load > Duplicates do not go away by waiting. An idempotent load (a `MERGE` keyed by order id over deduplicated input) would have left one copy. - The link between two Regions fails, and the app in one Region returns errors for order updates until it returns :: Netsplit > The Region chose to refuse writes rather than let the two Regions disagree. - :: Scan > A Scan is a specific way to read data, not one of these problems.

Which statement runs each operation?

--- shuffle_answers: true --- ## An online shop keeps its orders in an Iceberg table. Match each operation to the Athena statement that runs it. Not all options will be used. - Remove the orders of closed accounts :: `DELETE FROM orders WHERE …` > Athena's `DELETE` writes delete files that mark the removed rows. The data files stay as they were. - Merge small files, and files with deleted rows, into fewer larger files :: `OPTIMIZE orders REWRITE DATA USING BIN_PACK` > Bin-packing, merging files up to a target size, is the only way Athena compacts a table. - Drop snapshots older than a set age, and delete the files that no remaining snapshot uses :: `VACUUM orders` > One statement does both. The table property `vacuum_max_snapshot_age_seconds` sets how old a snapshot must be. - Add a column for the delivery method :: `ALTER TABLE orders ADD COLUMNS (delivery string)` > Only the table's metadata changes. No data file is rewritten. - :: `COMPACT TABLE orders` > Athena has no `COMPACT` statement. Compaction is `OPTIMIZE`. - :: `EXPIRE SNAPSHOTS orders` > Athena has no such statement. `VACUUM` expires snapshots. ## The same shop runs maintenance from a Glue job in Spark. Iceberg's maintenance procedures run with `CALL`, through the Iceberg catalog, which this job names `glue_catalog`. Match each operation to the Spark statement that runs it. Not all options will be used. - Remove the orders of closed accounts :: `DELETE FROM orders WHERE …` > `DELETE` is also Athena's statement. By default Spark rewrites the data files that held the rows (copy-on-write), unless the table property `write.delete.mode` is `merge-on-read`, which writes delete files as Athena does. - Merge small files, and files with deleted rows, into fewer larger files :: `CALL glue_catalog.system.rewrite_data_files(…)` > Iceberg's compaction procedure. Athena's `OPTIMIZE` takes none of these settings, and this procedure takes a strategy, a sort order and a target file size. - Drop snapshots older than a set age, and delete the files that no remaining snapshot uses :: `CALL glue_catalog.system.expire_snapshots(…)` > It drops the snapshots and deletes the files that only those snapshots used. - Delete files in the table's folder that no snapshot ever listed, such as files left by a failed write :: `CALL glue_catalog.system.remove_orphan_files(…)` > These are orphan files. The procedure can list them first with `dry_run => true`. Athena's `VACUUM` deletes them directly. - :: `CALL glue_catalog.system.optimize(…)` > Iceberg has no `optimize` procedure. `OPTIMIZE` is Athena's name for compaction, and Spark with Iceberg uses `rewrite_data_files`. - :: `CALL glue_catalog.system.vacuum(…)` > Iceberg has no `vacuum` procedure. `VACUUM` is Athena's name, and in Spark the same work is two calls, `expire_snapshots` and `remove_orphan_files`.

What does each operation change?

The shop’s orders table has one folder per order day. Each hour a job appends a few small files, and last week the shop deleted, in Athena, the orders of customers who closed their accounts.

--- shuffle_answers: true --- ## For each goal, choose the operation that achieves it. Each option may be used once, more than once, or not at all. - Queries no longer read the delete files from last week's deletions :: Compaction > Compaction rewrites each data file without its deleted rows, so later queries have no delete files to read. In Athena: `OPTIMIZE`. In Spark: `rewrite_data_files`, then `rewrite_position_delete_files` to clear delete files that still point at rewritten data files. - Each day's many small files become a few large files :: Compaction > Compaction merges small files up to a target size. In Athena: `OPTIMIZE`. In Spark: `rewrite_data_files`, which can also sort the rows. - Files in S3 take less space than before last week's deletions :: Snapshot expiry > The old files stay in S3 while an older snapshot still lists them. Snapshot expiry drops those snapshots and deletes the files only they used. In Athena: `VACUUM`. In Spark: `expire_snapshots`. - Time-travel queries can no longer return the deleted orders :: Snapshot expiry > Until the old snapshots are expired, a time-travel query can still read the files that hold those orders. In Athena: `VACUUM`. In Spark: `expire_snapshots`. - :: Deleting rows > Deleting rows, with `DELETE` in Athena and Spark, adds new files and keeps the old ones in S3, so on its own it meets none of these goals. ## The shop runs one `DELETE` on the orders table in Athena. Which statements are true right after it? Select all that apply. - [x] No data file was rewritten > Athena writes delete files that mark the rows. It does not rewrite the data files. - [x] More files in the table than before > Each `DELETE` statement adds delete files. Compaction later folds them into rewritten data files. - [x] Time travel to before the `DELETE` shows the deleted rows > The earlier snapshot lists the same data files and none of the new delete files. - [ ] Less storage in S3 than before > Nothing is removed from S3. The delete files add a little storage. - [ ] Queries read fewer files than before > Queries now read the delete files as well as the data files, until compaction. ## You run compaction (`OPTIMIZE`) and then list the table's folder in S3. It holds more data than before. Why? 1. [x] Earlier snapshots still list the old data and delete files > Compaction writes new files and commits a new snapshot. The old files still belong to earlier snapshots until snapshot expiry (`VACUUM`) drops them. In Spark: `expire_snapshots`. 1. [ ] Compaction keeps the delete files, which now apply to the new files > The new files are written without the deleted rows, so the new snapshot lists no delete files. The old delete files stay only for the earlier snapshots. 1. [ ] Compaction keeps a backup copy of the table for safety > No backup is made. Compaction writes only the new, merged files.

Athena or Spark?

--- shuffle_answers: true --- ## For each maintenance need on an Iceberg table, choose where you can do it. Each option may be used once, more than once, or not at all. - Compact only one day's folder, not the whole table :: Athena or Spark > Athena's `OPTIMIZE … WHERE` on the day column, or Spark's `rewrite_data_files` with a `where` filter. - Sort the rows inside each file by order time during compaction :: Spark only > Athena's `OPTIMIZE` only merges files and keeps the rows in the order they were written. Spark's `rewrite_data_files` takes `strategy => 'sort'`. - Choose the target size of the files that compaction writes :: Spark only > Athena picks the target size itself, and none of its table properties sets it. Spark's `rewrite_data_files` takes `target-file-size-bytes`. - Compact only the files holding one store's orders, when the table has one folder per day, not per store :: Spark only > Athena's `WHERE` in `OPTIMIZE` accepts only the columns the folders are named by. Spark's `where` filter can name other columns. - Expire snapshots older than a set age :: Athena or Spark > Athena's `VACUUM` uses the table property `vacuum_max_snapshot_age_seconds`. Spark's `expire_snapshots` takes `older_than` in each call. - List orphan files, which no snapshot ever listed, before deleting them :: Spark only > Spark's `remove_orphan_files` with `dry_run => true`. Athena's `VACUUM` deletes them directly. - Run maintenance as queries in the query editor, without starting a job or a notebook session :: Athena only > Athena runs `OPTIMIZE` and `VACUUM` as queries. Spark needs a Glue job or a notebook session. - Pay for compaction by the data it scans, not by worker time :: Athena only > Athena bills `OPTIMIZE` by the data scanned during the rewrite. A Glue job or session bills its DPUs for the time it runs. - :: Neither > Each need here can be met in Athena, Spark or both.

How a job writes and reloads a table

--- shuffle_answers: true --- ## A Glue job reads a week of orders and calls `repartition(8)`, which spreads the rows evenly over 8 Spark partitions without looking at their day. So each Spark partition holds orders from all seven days. The job writes them to a table with one folder per day, with `write.distribution-mode = none`, so Spark does not regroup the rows by day before writing. How many files does each day's folder get? 1. [x] 8, one from each task > Each task writes one file into every day folder it has rows for, and here every task has rows for every day. 1. [ ] One > One file per day needs the rows regrouped by day before writing, which `write.distribution-mode = hash` does. 1. [ ] 56, eight for each of the seven days > 56 is the number of files for the whole week, across all seven folders. ## A Glue job appends one day of orders to the table on each run. A run finishes successfully, and then someone presses **Run** in the console again. What does the table hold? 1. [x] Every order of that day twice > An append doesn't check what is already loaded. To make the load safe to repeat, delete that day before writing it, as you did to repair the double load in the Athena tutorial. A `MERGE` on a key also works. 1. [ ] Every order of that day once, because Iceberg skips duplicate rows > Iceberg has no unique-key check on append. 1. [ ] Every order of that day once, because Glue stops a duplicate job run by default > By default Glue allows one run of a job at a time, so it refuses a second start only while the first run is still going. After the first run succeeds, the second run starts and appends the day again.

Terms used on this page

System of record. The store with the authoritative copy; other copies are derived from it.

Operational system (OLTP), analytical system (OLAP), point query. Many small reads and writes by key, in milliseconds; scans and aggregates over many records; one record fetched by its key.

Row-oriented, column-oriented. One record’s values stored together; one column’s values stored together.

Item, partition key, sort key. DynamoDB’s record; the key part that picks its storage partition; the optional part that orders items sharing a partition key.

GetItem, Query, Scan. One item by key; the items of one partition key; every item.

Read request unit / write request unit. One strong read (or two eventual) of up to 4 KB; one write of up to 1 KB.

Export, federated query, derived copy. A copy of the store’s items written to S3 (all, or those changed in a time window); a query that reads the store through a connector; a result computed elsewhere and written back.

Partial failure, timeout, netsplit. Some parts fail; giving up waiting; nodes that cannot reach each other.

Replication, sharding. The same data on several nodes; a different slice on each node.

Replica, leader, follower. A copy on another node; in single-leader replication, the one that takes writes; the ones that copy from it.

Region, Availability Zone (AZ). A geographic area; one or more isolated data centres (buildings of nodes) in a Region, with their own power and network.

Synchronous, asynchronous, majority (quorum). “done” after the required followers have it; after the leader’s own commit; after more than half have it.

Replication lag, eventual consistency, read-after-write. A follower behind the leader; agreement if writes stop, no deadline; your reads show your writes.

Linearizability. Behaves as one copy, in real-time order; “strong consistency” is a vague name for it.

Eventually / strongly consistent read. Any replica, may be old, 0.5 units per 4 KB; the leader, the latest value including every write finished before the read, 1 unit per 4 KB.

CAP, PACELC. During a netsplit, linearizable or a non-error answer from every working node; else, latency or consistency.

Lost update, compare-and-set, conditional write, optimistic concurrency. The second write replaces the first; write only if unchanged; DynamoDB’s form; check at the end, retry if changed.

Transaction, ACID, BASE. A group that succeeds or fails whole; atomicity, consistency, isolation, durability; mostly “not ACID”.

Serializability. The outcome of concurrent transactions equals running them one at a time.

Timeliness, integrity, idempotent. Shows the latest; nothing lost or duplicated; twice has the effect of once.
