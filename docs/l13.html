When does a replicated store answer “done”?

A recap of L12: one leader, two followers, and when the leader confirms a write.

--- shuffle_answers: true --- ## A ticket app keeps seat availability in a store with one leader and two followers. The app sends the leader a write: seat 14C is sold. For each situation, choose the kind of replication that produces it. Each option may be used once, more than once, or not at all. - Leader answers "done" only after both followers have the change :: Synchronous > A confirmed write survives the loss of the leader, because both followers have it. A majority would have answered after the first follower had the change. - Leader fails right after answering "done", before any follower has the change, and the write is lost :: Asynchronous > A confirmed write that only the leader had is lost when a follower without it takes over. - Leader answers "done" after the faster of its two followers has the change :: Majority (quorum) > Two of three replicas have it, so losing any one replica keeps the write. DynamoDB works this way. The leader waited for one follower, which asynchronous replication never does. - Leader answers "done" right after its own commit, while it sends the change to the followers :: Asynchronous > The leader waits for no follower, so writes are fast, and a confirmed write may exist only on the leader. - Every confirmed write survives the loss of any one replica, and one slow follower does not delay writes :: Majority (quorum) > The leader waits for one of its two followers, so every confirmed write is on two of the three replicas, and losing any one still leaves a copy. The leader does not wait for the slower follower, which gets the change a little later. Synchronous replication also keeps the write safe, but there the slow follower delays every write. - One slow follower makes every write wait :: Synchronous > The leader cannot answer until every follower it waits for has the change, so the slowest one sets the pace. - :: Linearizable > Linearizability is about what a read may return after a write has finished. It does not say how many followers must have the change before the leader answers "done".

What may the buyer’s read return?

A recap of L12: a follower that is behind, and the two kinds of DynamoDB read.

--- shuffle_answers: true --- ## A ticket app keeps seat availability in DynamoDB. The seller marks seat 14C "sold" and reads it back from the leader: "sold". No other write changes seat 14C. The seller then texts the buyer. A moment later the buyer's app reads seat 14C from a follower that is behind and gets "available". Which statements are true? Select all that apply. - [x] Buyer's read is not linearizable > The buyer's read started after the seller's read had returned "sold", and no later write changed the seat. A linearizable read would have to return "sold". - [x] Buyer's app used an eventually consistent read > A strongly consistent read goes to the leader. A read served by a follower that is behind was an eventually consistent read. - [x] Strongly consistent read by the buyer would have returned "sold" > In DynamoDB a strongly consistent read goes to the leader, which has the latest write. - [ ] Strongly consistent read uses the same read units as an eventually consistent one > A strongly consistent read uses 1 read unit per 4 KB, an eventually consistent read 0.5. - [ ] Strong reads alone stop two buyers from both buying seat 14C > Both buyers can read "available" correctly at the same moment, then both write. Preventing that needs a conditional write, which checks and writes in one step.

What reaches each copy?

Polling, the change stream and the outbox, after a few fast changes and one delete.

--- shuffle_answers: true --- ## Between two polls, within one minute, the app moves trip t-0042 from accepted to arrived to started. Then a cleanup job deletes trip t-0091, which every copy already holds, from the table directly, without going through the app. For each way of getting changes out, choose what reaches the copy. Not all options will be used. - Poll the table every 5 minutes on an updated-at column :: Latest status only, without the delete > Each poll sees only the state at the moment it asks, so the two changes between two polls reach the copy as one. A deleted item matches no query, so the copy never learns of the delete. - Read the table's change stream :: Every status change, with the delete > The stream is the store's own record of changes. It carries every change in order for each item, including deletes, whoever made them. - Write an outbox row in the same transaction as each change the app makes :: Every status change, without the delete > The outbox holds only what the app wrote. The cleanup job wrote no outbox row, so the copy never learns of the delete. - :: Latest status only, with the delete > Only the stream sees a deleted item. A poll finds nothing to return, and the outbox holds only what the app wrote. - :: Nothing until tomorrow's export > That is what a nightly export gives. Each of these three ways gets changes to the copy within minutes or seconds.

Which way meets each requirement with the slowest refresh?

Data latency requirements in EARS, and the four ways to keep a copy up to date.

--- shuffle_answers: true --- ## A food-delivery app keeps orders in DynamoDB. Each 20-minute load ends before the next starts. The daily load runs from 02:00 to 03:00. For each requirement, choose the way that meets it with the slowest refresh, and of two that refresh equally often, the cheaper one. Each option may be used once, more than once, or not at all. - WHEN the monthly invoice runs on the 1st at 06:00, INVOICING SHALL include every order delivered before the 1st at 00:00 :: Data lake, daily partitions > The 02:00 load adds the finished day and finishes by 03:00, so every order delivered before 00:00 is in by 06:00. A fresher way adds nothing the invoice needs. - WHILE orders are open, KITCHEN SCREEN SHALL show each new order with data latency under 10 s at p99 :: Streaming > Only a stream gets each change to the reader within seconds. A 20-minute load misses the target on every order. - WHEN the restaurant dashboard refreshes, DASHBOARD SHALL show orders with data latency under 1 h at p95 :: Lakehouse, delete files, every 20 min > A 20-minute load meets the hour with time to spare, and readers always see one whole snapshot. A daily load can be a day behind. A stream also meets the hour, with more freshness than the dashboard needs. - WHEN the tax report runs at 06:00 the day after a quarter ends, REPORT SHALL include every order of the quarter :: Data lake, daily partitions > The daily load of the quarter's last day finishes by 03:00, so every order is in by 06:00. A fresher way adds nothing the report needs. - WHILE couriers are on shift, DISPATCH SHALL see each order's status with data latency under 30 s at p95 :: Streaming > 30 seconds is far below a 20-minute schedule. Each status change has to reach dispatch as it happens. - WHEN a manager opens the shift summary, SUMMARY SHALL show sales with data latency under 1 h at p99 :: Lakehouse, delete files, every 20 min > A 20-minute load meets a p99 of 1 h as long as each run takes well under 40 minutes. - :: Data lake, rewritten every 20 min > It refreshes every 20 minutes, as the lakehouse does, and costs more, \$4.15 a day against \$1.29 in the cost table for the rides app. Readers can also see half-replaced files while it runs.

Terms used on this page

System of record. The store with the authoritative copy; other copies are derived from it.

Operational system (OLTP), analytical system (OLAP), point query. Many small reads and writes by key, in milliseconds; scans and aggregates over many records; one record fetched by its key.

Row-oriented, column-oriented. One record’s values stored together; one column’s values stored together.

Item, partition key, sort key. DynamoDB’s record; the key part that picks its storage partition; the optional part that orders items sharing a partition key.

GetItem, Query, Scan. One item by key; the items of one partition key; every item.

Read request unit / write request unit. One strong read (or two eventual) of up to 4 KB; one write of up to 1 KB.

Export, federated query, derived copy. A copy of the store’s items written to S3 (all, or those changed in a time window); a query that reads the store through a connector; a result computed elsewhere and written back.

Partial failure, timeout, netsplit. Some parts fail; giving up waiting; nodes that cannot reach each other.

Replication, sharding. The same data on several nodes; a different slice on each node.

Replica, leader, follower. A copy on another node; in single-leader replication, the one that takes writes; the ones that copy from it.

Region, Availability Zone (AZ). A geographic area; one or more isolated data centres (buildings of nodes) in a Region, with their own power and network.

Synchronous, asynchronous, majority (quorum). “done” after the required followers have it; after the leader’s own commit; after more than half have it.

Replication lag, eventual consistency, read-after-write. A follower behind the leader; agreement if writes stop, no deadline; your reads show your writes.

Linearizability. Behaves as one copy, in real-time order; “strong consistency” is a vague name for it.

Eventually / strongly consistent read. Any replica, may be old, 0.5 units per 4 KB; the leader, the latest value including every write finished before the read, 1 unit per 4 KB.

CAP, PACELC. During a netsplit, linearizable or a non-error answer from every working node; else, latency or consistency.

Lost update, compare-and-set, conditional write, optimistic concurrency. The second write replaces the first; write only if unchanged; DynamoDB’s form; check at the end, retry if changed.

Transaction, ACID, BASE. A group that succeeds or fails whole; atomicity, consistency, isolation, durability; mostly “not ACID”.

Serializability. The outcome of concurrent transactions equals running them one at a time.

Timeliness, integrity, idempotent. Shows the latest; nothing lost or duplicated; twice has the effect of once.

Data latency (freshness)

Data latency. The time from a change in the source to the moment a reader can see it in its copy. DDIA calls the property data freshness.

Service level objective (SLO). A target for a measured quantity, often a percentile.

Service level agreement (SLA). An agreement that states the SLOs and what users get when they are missed.

Dual write. The application writes the same change to two systems itself, and no transaction covers both.

Change log. A store’s own append-only record of every change.

Change data capture (CDC). Reading a store’s change log and turning each change into an event that other systems read.

Snapshot. A copy of the whole table at one time, which a new copy starts from before it follows the log.

Outbox table. A table the application writes each outgoing event to, in the same transaction as the change.

Polling. The reader asks the source for new data every T seconds.
