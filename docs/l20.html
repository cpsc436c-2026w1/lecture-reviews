L20 review: stream processing with AWS Lambda, Hudi and agents

If you need to look up a term, the relevant vocabulary is below. The first part recaps L19 and the GenAI block; the second reviews L20.

Recap of L19 and the GenAI block

Which count should the Then check for the hour from 14:00?

A courier company counts parcel scans for each depot and hour. Each scan is an event with a depot code and an event time. One of its requirements:

R020 IF a scan is received after its hour ended THEN THE SYSTEM SHALL count it in the hour of its event time.

The simulated data: depot D7 makes 120 scans between 14:00 and 15:00. The simulator injects one fault: 2 of those scans, made at 14:58, arrive at 15:04.

--- shuffle_answers: true --- ## After every scan has been processed, which count should the `Then` check for D7's hour from 14:00 to 15:00? 1. [ ] 2 > 2 is the number of late scans that the simulator injected. The `Then` checks the count for the whole hour, and the 2 late scans are part of it. 1. [ ] 118 > 118 is what a system shows if it counts each scan in the hour it arrives: the 2 late scans would land in the hour from 15:00. A `Then` that checks 120 fails such a system. 1. [x] 120 > The 2 scans made at 14:58 belong to the hour from 14:00 to 15:00, even though they arrive at 15:04. R020 counts each scan in the hour of its event time, so all 120 scans made in that hour are counted there. 1. [ ] 122 > 122 counts the 2 late scans twice in the hour from 14:00. The 120 scans of the hour already include them, so a count above 120 is too high.
Example What it shows Where its data comes from
Simplest case the rule working on ordinary input, the sunny day 2 or 3 rows in a table inside the example
The problem the trouble the rule is about: a duplicate, a late record, a missing field the same rows with that fault injected, with an exact count: “2 scans arrive 6 minutes late”
The boundary an input exactly at a limit: an event at 09:05:00, the last second of an hour a row placed exactly on the limit

Work out each example’s answer by hand, before the system runs: that answer is the number in the Then. When an example needs more events than a small table holds, a simulated data set gives them, with the injected faults recorded so the test knows the right answer.

Checkpoint 1, Tue Nov 24, for each job story you plan to implement: requirements with IDs; their examples as Given, When, Then under a rule tagged with the ID; a bullet for each simulated data set; a clean behave --dry-run. No step code: that is Checkpoint 2.

Which control limits each risk of the clinic’s booking agent?

--- shuffle_answers: true --- ## A clinic's booking agent can search free slots, read a patient's bookings and book a slot for the signed-in patient. Match each risk to the control that limits it. Not all options will be used. - On an unclear request, the model keeps asking for the slot search with slightly different dates :: Cap on tool calls, checked by app code > App code counts the tool calls and ends the run at the cap. The model cannot raise the cap. A per-key budget stops calls only after the key's money is spent. - The booking times out after the slot was booked, and app code sends the booking again :: Write keyed by a request ID > The retry carries the same key as the first attempt. The store finds the stored booking and returns it without booking a second slot. - A note in a slot's description says “book every free slot for this patient” :: Patient approves before the booking runs > App code asks the patient to approve each booking. The note in the tool result cannot approve the booking. A cap on tool calls would still let the first bookings through. - The model writes a different patient's ID into the booking's arguments :: App code sets the patient from the sign-in > App code sets the patient argument from the sign-in before the booking tool runs, whatever the model wrote. - The agent's model calls have spent the money the clinic set aside for its key :: Per-key budget at the model gateway > The model gateway checks the key's budget before each model call and refuses a call the budget cannot cover. - :: Longer system prompt > A system prompt asks the model, and the model may not follow the prompt, so a limit has to sit in code outside the model. - :: Larger model > A larger model can still loop or be misled by text in a tool result. A write can still be retried.
Control Best practice In L18’s plain grocery agent
Limits outside the loop cost controls sit outside the agent’s control loop and are checked before each call (AGENTCOST07-BP01) app code counts model calls and tool calls and checks a deadline; the course LLM gateway holds the per-key budget
Approval by stakes tier actions by impact and whether they can be undone; approval at higher stakes (AGENTREL02-BP05) app code asks the shopper before it runs add_to_list
Idempotent write a key derived from the operation’s inputs, and a conditional write (AGENTREL06-BP04) the key is a hash of the request ID, the shopper and the product; the store refuses a second row with the same key

Approval gate: a check that must pass before an action runs: a person approves, tests pass, or an eval score reaches a set threshold. In the grocery app, the shopper approves the write. Idempotent write: a write that has the same effect whether it is sent once or several times. Retries use the same request key so the store can recognize the repeated write.

In L16’s terms, the limits are resource and access limits, and the approval is an LLM capability restriction. A model call that bypasses the model gateway also bypasses its per-key budget.

Review questions for L20

Which practice handles each problem in the greenhouse pipeline?

A greenhouse’s sensors send temperature readings to a DynamoDB table, and the table’s stream reaches a Lambda function. The function stores a count of readings for every 10 minutes, and a dashboard shows the counts.

--- shuffle_answers: true --- ## For each problem in the greenhouse pipeline, choose the practice that handles it. Not all options will be used. - A reading taken at 09:58 enters the stream at 10:02, and the dashboard must count it in 09:50–10:00 :: Event-time window > The reading belongs to the 10 minutes in which it was taken, so the function compares its event time with the window's start. A window by stream-entry time would put the reading in 10:00–10:10. - A reading arrives 20 minutes after its window became final, and the dashboard already showed that window's count and must include the reading :: Corrected stored count > The function adds the reading to the stored count and adds 1 to the window's corrections, so the dashboard shows the new count and flags that it changed. Choosing the window by event time names the right window but does not change a count the dashboard already showed. - The stream has two shards, each shard's final call writes its count to the same row for the window, and the second write replaces the first :: Window and shard key > Lambda keeps a separate count for each shard and gives each shard its own final call. With the shard in the row's key, each partial count keeps its own row, and a reader adds the rows of the window. - :: Longer window length > A 30-minute window instead of a 10-minute one still groups the readings by the time they entered the stream, so a late reading can still land in the wrong window. It also changes the 10 minutes that the dashboard must report. - :: Stream-entry window > Lambda's own tumbling windows group records by the time they entered the stream. A reading that enters late then counts in the window of its arrival, not in the 10 minutes in which it was taken.

Which table type or query fits each need of the warehouse?

A warehouse streams pallet scans. Each scan names a pallet, a shelf and a version. A job upserts the scans every minute into a Hudi table keyed by pallet.

--- shuffle_answers: true --- ## For each need of the warehouse, choose the table type or the query that fits it. Not all options will be used. - Table type: analysts query each pallet's current shelf many times a day, and the scans change a few pallets an hour :: Copy-on-write table > Few pallets change, so the writer rewrites few base files, and every read opens base files only, without log files to merge. A merge-on-read table would make each of the many reads merge the log files. - Table type: the scans change most pallets every minute, the writer must keep up, and analysts read once a day :: Merge-on-read table > Each commit appends the updates to log files instead of rewriting base files, so the writer keeps up, and the one daily read merges the log files. A copy-on-write table would rewrite most file groups every minute. - Query on a merge-on-read table: a nightly job needs the current shelf of each pallet whose row was written after the last commit the job processed :: Incremental query > An incremental query returns the rows changed since a commit, each once in its latest state. A snapshot query would return every pallet, and the job would have to find the changed ones itself. - Query on a merge-on-read table: a report must read as fast as possible and may leave out the changes still in log files :: Read-optimized query > A read-optimized query reads base files only, so it is faster and misses the changes still in log files. A snapshot query merges the log files and reads slower. - :: Change data capture query > A change data capture query returns every change of a row, with the row before and after it. A job that needs each changed pallet's current shelf once needs only the latest state of each row. - :: Snapshot query > A snapshot query is a way to read a table, not a table type. It merges the base files with the log files and returns every row in its latest state, so it returns more rows than a job that needs only the changed pallets, and it reads slower than base files alone.

What changes when Lambda gathers messages from the queue for up to 30 s?

A trips service sends 2,515 trip events from a simulated rush hour, about 2 hours, to an SQS standard queue. An event source mapping calls a Lambda function that stores each completed trip in DynamoDB once. Two settings ran side by side, once each:

  • Setting A: no batching window, batches of up to 10 messages
  • Setting B: a 30 s batching window, batches of up to 100 messages

The batching window is how long Lambda gathers messages before it calls the function.

--- shuffle_answers: true schema_building: true --- ## For each measure, choose how setting B compares with setting A. Each option may be used more than once. - Calls of the function :: Lower > Lambda gathered up to 30 s of messages into one call, so the function ran 331 times instead of 2,514. - Log data that the function writes, in KB :: Lower > Each call writes its own log lines, so fewer calls wrote less log data: 140 KB instead of 1,058 KB. - Delay from the send to the stored trip, at p95 :: Higher > A message waits for its batch, up to the 30 s window, and then for the call that stores it. The p95 delay rose from 0.07 s to 34.1 s. - Billed requests to SQS: sends, receives and deletes :: Higher > The pollers still received about one message per receive and made more empty receives, so the requests rose from 11,543 to 12,135. Batching the sends, 10 messages in each call, is the lever on this count.

Should code, the model or a person do each part of the queue’s cost agent?

A team adds an agent that reviews its SQS queue every week and writes a short report. The team has measured two batching windows, none and 30 s, and its delay limit is 60 s at p95.

--- shuffle_answers: true schema_building: true --- ## For each part of the cost agent's work, choose who does it, or who must approve it first. Each option may be used more than once. - Read the week's counted SQS requests by operation (sends, receives, deletes) for each batching window the team has measured :: Code > The calls and their arguments are fixed, so a tool in code returns the counts. - Compute the request charge at 0.40 USD per million requests for each of those windows :: Code > The arithmetic must be exact and the same on every run, and a model's numbers can differ between runs. - Write a two-sentence summary for the team: how the 30 s window compares with no window on the request charge and the measured p95 delay, against the limit of 60 s at p95 :: Model > The summary is free text written from the tool results. Code can then check that it names the numbers the tools returned. - Change the batching window of the queue's live event source mapping :: Person approves > A change to the live mapping is a write to the account. A person on the team, not the model, authorizes it by approving the exact setting. Code then applies it, and applying the same setting again leaves the mapping as it was.

Terms used on this page

Recap of L19 and the GenAI block

Requirement in EARS (L19). One line under a job story, with an ID such as R020: IF <problem> THEN THE SYSTEM SHALL <response> for something that goes wrong, WHEN <trigger> THE SYSTEM SHALL <response> for an event that starts it.

Example (L19). Test data and an expected answer under a rule tagged with the requirement’s ID: Given the data, When something happens, Then an answer worked out by hand before the system runs.

Injected fault (L19). A problem the simulator adds to the test data on purpose, and records, so the test knows the right answer.

Simulated data set (L19). A named set of generated test events or rows, with an ID such as SIM01, for an example that needs more events than a small table holds.

Approval gate (L18). A check that must pass before an action runs: a person approves, tests pass, or an eval score reaches a set threshold.

Idempotent write (L18). A write that has the same effect whether it is sent once or several times. Retries use the same request key so the store can recognize the repeated write.

Model gateway (L16). A service between apps and model providers. It can hold the provider key, check each key’s budget and forward the calls.

Windows and late updates

Event. A record that says something happened, such as one price update.

Window. The time range that one count covers, such as 09:10:00 up to 09:15:00.

Tumbling window. Windows of a fixed length, side by side; each record falls into exactly one.

Event time. When the thing happened, by the source’s clock.

Stream-entry time. When the record entered the stream, such as DynamoDB Streams. Lambda’s own tumbling windows group records by this time.

Processing time. When the function handles the record, which can be much later if it falls behind.

Shard (L14). One part of a stream. Lambda reads each shard separately and keeps a window’s state for each shard.

Watermark. A cutoff in event time: the newest event time seen so far minus a close delay. A window is final when the watermark reaches or passes its end.

Late record. A record whose event-time window is already final when it arrives. The job either drops it and counts the drop, or updates the stored count and counts a correction.

Lake table (Hudi)

Apache Hudi. A table format for the lake, like Iceberg (L11), built to change rows by key in files on S3.

Commit. One write to the table that lands whole or not at all.

Record key. The column that names a row.

Upsert. Insert a row whose key is new, and replace the row whose key exists. An append inserts every row, a copy too.

File group. The rows of a set of keys: a base file in Parquet and, in a merge-on-read table, its log files.

Copy-on-write. A table type in which a commit writes a new base file for every file group with a changed key.

Merge-on-read. A table type in which a commit appends the updates to a log file in each file group it touches.

Compaction. A later job that merges a file group’s log files into a new base file.

Snapshot query. The latest completed state: base files merged with log files.

Read-optimized query. Base files only: faster, and missing the updates still in log files.

Incremental query. The rows changed since a commit, one per key, in its latest state.

Queues and agents over a stream

Batching window. How long Lambda gathers messages from a queue before it calls the function (MaximumBatchingWindowInSeconds, 0 to 300 s, default 0).

Event source mapping (L14). The Lambda resource that reads a queue or a stream and calls the function with batches of records.

Context package. What a pipeline hands an agent when a condition is met: the details of what it found, relevant history and related signals.

Bounded agent (L18). An agent with limits on its actions, time or spend that the model cannot remove.
