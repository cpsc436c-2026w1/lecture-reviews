Storage side of scaling up

What does each filter condition make Spark read?

A city library keeps its loan records for September to December 2025 in S3 as Parquet, one folder partition per month of loan_date:

s3://city-library/loans/
├── month=2025-09/
│   └── part-0.parquet        about 150 MB
├── month=2025-10/
│   └── part-0.parquet
├── month=2025-11/
│   └── part-0.parquet
└── month=2025-12/
    └── part-0.parquet

Each file holds only its month’s loans, in many row groups (the blocks of rows inside a Parquet file). Inside a file the rows are sorted by branch_id (the library has 40 branches); the loan_days column is in no particular order, and every row group has some loans longer than 21 days. Spark on an EMR cluster runs queries that each have one filter condition, and each condition matches some loans. Assume the reader rules out row groups only by their min and max.

--- shuffle_answers: true --- ## For each filter condition on the loans folder, what does Spark open and read? Each option may be used once, more than once, or not at all. - `month = '2025-11'` :: 1 or 2 files opened, every row group read > The condition names the folder partition key, so Spark opens the November 2025 folder and rules out the other 3 by their names, without reading their row groups. Every row in the November 2025 file is a November 2025 loan, so every row group is read. - `month IN ('2025-11', '2025-12')` :: 1 or 2 files opened, every row group read > The condition names the folder partition key, so Spark opens the November 2025 and December 2025 folders and rules out the other 2 by their names, without reading their row groups. Every row in those two files is a November 2025 or December 2025 loan, so every row group of both is read. - `branch_id = 17` :: all 4 files opened, some row groups may be skipped > All 4 files are opened, because the condition does not name `month`. Inside each file the rows are sorted by branch, so each row group has a narrow `branch_id` range. Where the writer stored each row group's min and max in the footer, the reader skips the row groups whose range does not include 17, without fetching those row groups. - `loan_days > 21` :: all 4 files opened, every row group read > The condition does not name `month`, so Spark opens all 4 files. Every row group has some loans longer than 21 days, so each row group's maximum `loan_days` is above 21 and the footer rules none out. Without a sort, values usually spread like this, but not always: a row group whose maximum happened to be 21 or less would be skipped. - :: footers read, no row group read > A footer records where the row groups are and each row group's min and max; the footer holds no rows. Footers alone answer a query only when their min and max rule out every row group. Each condition here leaves at least one row group to read: the `month` conditions name folders that hold loans, and each of the other conditions matches some loans, so at least one row group holds a matching row and has to be read.

Which folder partition key best supports the analysts’ one-day and one-month queries?

A news site keeps its page views from January 2024 to December 2025 in S3 as one Parquet file, with no folder partitions:

s3://news-site/page-views/
└── page-views.parquet    4 GB, rows sorted by view time, many row groups

The analysts query the file with DuckDB. Their common queries filter on the view time, one day or one month, and count views per article category. The team will rewrite the file into folder partitions on one key, and the analysts will write each time filter so that it also names that key. The rewrite keeps the rows sorted by view time, with many row groups in each file. DuckDB recommends at least 100 MB per folder partition.

--- shuffle_answers: true --- ## Which folder partition key best supports the analysts' one-day and one-month queries? 1. [x] `month`: 24 folders of about 170 MB > Each query names one month, so it opens one folder. Inside that folder, the footer's minimum and maximum view times let a daily query skip other days' row groups, and each folder partition is over 100 MB. A `day` key would also let a daily query open one folder, but each folder would hold only about 5.5 MB, below DuckDB's 100 MB guidance, and a monthly query would open about 30 of them. 1. [ ] `day`: 731 folders of about 5.5 MB > The `day` key matches the daily filter, but each 5.5 MB folder partition is below the 100 MB guidance. A monthly query opens about 30 small folder partitions, one per day of the month, while sorting by view time already lets a daily query skip row groups within a monthly folder partition. 1. [ ] `category`: 12 folders of about 330 MB > The queries group by category and filter on dates. Every query needs all 12 categories, so it opens all 12 folders and the key rules nothing out.

Which changes spread the scan over all four threads?

A hotel chain exports its 2025 bookings as one Parquet file:

bookings-2025.parquet     1.2 GB, 30 million rows, one row group

About 2.5 million of the rows are July 2025 bookings. DuckDB with four threads on an m6a.xlarge (4 vCPU, 16 GiB) computes the average nightly price per hotel for July 2025 in 3 s. During the query one vCPU is busy and three stay idle. Every rewrite below writes row groups of about 100,000 rows unless the option says otherwise.

--- shuffle_answers: true --- ## Which of these changes let the July query finish sooner by spreading its scan over all four threads? Select every change that does. - [x] Rewrite the file with row groups of about 100,000 rows > At about 100,000 rows each, the 30 million rows make about 300 row groups. DuckDB gives each thread whole row groups to read, so the four threads share the scan. - [x] Rewrite the bookings file as folder partitions by month, one file per month > At about 100,000 rows per row group, the 2.5 million July 2025 rows make about 25 row groups in the July 2025 file. DuckDB gives each thread whole row groups to read, so the four threads share the scan. The query opens only the July 2025 file when its filter names the `month` key; with a filter on the booking date alone, DuckDB opens all twelve files, and their footers rule out the other months' row groups. - [ ] Rewrite the bookings file as one Parquet file sorted by hotel, still one row group > The file has one row group, so one thread reads it and the other three have nothing to read. Sorting changes which rows sit next to each other inside the row group; the file still has one row group for DuckDB to give its threads. - [ ] Set DuckDB to 32 threads > The file has one row group, so one thread reads it and the extra threads have nothing to read. The instance has only 4 vCPUs to run the threads. - [ ] Move to an m6a.2xlarge (8 vCPU, 32 GiB) > The file has one row group, so one thread reads it and the extra vCPUs have nothing to read. More memory does not increase the number of row groups.

Scaling out: more nodes, and a network between them

Which first change cuts the daily query’s time most?

A parcel company keeps three years of parcel scans as CSV in S3:

s3://parcel-co/scans/
├── part-0.csv
│   …
└── part-N.csv            450 GB in all, 25 columns, 2023 to 2025

A query that runs every day counts late parcels per depot for one month and reads 3 of the 25 columns. On one m6a.xlarge it takes 50 minutes. The instance reads from S3 above its baseline network rate only for the first minutes; for most of the 50 minutes it reads at the m6a.xlarge’s baseline of 1.56 Gbps, about 195 MB/s, and reading all 450 GB at that rate takes about 38 minutes.

--- shuffle_answers: true --- ## Which first change is likely to cut the daily query's time most? 1. [x] Convert the CSV once to Parquet > The query then fetches only 3 of the 25 columns, compressed and stored as typed values, so most of the 450 GB is not sent over the network. With its data converted to Parquet, L1's taxi query went from 14 min to 5.5 s on one instance. Three nodes cut the time to about a third at best, while reading 3 of 25 columns already cuts the data fetched to about an eighth, before compression, so the Parquet change cuts more. 1. [ ] Run the query on EMR with three m6a.xlarge core nodes > Three m6a.xlarge nodes have about three times the network capacity of one, so the query takes at best about a third of the time, and the three nodes still read every byte of the CSV. 1. [ ] Split the CSV into many smaller files > Smaller files hold the same 450 GB in total, and every byte is still read over the same network.

Which node type should the team add for this job? *

An EMR cluster with one primary node and two core nodes runs a long Spark job that reads its input from S3 and writes its results back to S3. To finish the job sooner, the team wants to add nodes for it and remove them soon afterwards, without losing any data the cluster stores.

--- shuffle_answers: true --- ## Which node type should the team add for this job? 1. [x] Task nodes > Task nodes run executors and store no HDFS blocks, so they can be removed as soon as the job ends; the input and the results stay in S3. 1. [ ] Core nodes > Core nodes run executors and store HDFS blocks, which exist only on the cluster, so removing a core node risks losing those blocks. The team should not add core nodes for one job and remove them afterwards. 1. [ ] Larger primary node > The primary node manages the cluster and coordinates its services. The job's parallel work runs in executors on the core and task nodes, so enlarging the primary adds no capacity for that work.

After how many queries has the rewrite paid back? *

Vancouver publishes its Van311 non-emergency service requests as open data. A team keeps five years of them in S3 as one CSV file per year, and a weekly query reads them all:

s3://van-311/requests/
├── 2021.csv
│   …
└── 2025.csv

Rewriting the CSV files once as sorted Parquet in folder partitions uses 1,200 CPU-seconds. The weekly query uses 50 CPU-seconds on the CSV and 10 CPU-seconds on the rewritten files.

--- shuffle_answers: true --- ## After how many weekly queries has the rewrite paid back its CPU-seconds? 1. [x] 30 queries > Each query saves 50 − 10 = 40 CPU-seconds, and 1,200 / 40 = 30 weekly runs. 1. [ ] 24 queries > 1,200 / 50 divides by what the old query cost. The rewrite is paid back by what each query saves, 40 CPU-seconds. 1. [ ] 120 queries > 1,200 / 10 divides by what the new query costs. The rewrite is paid back by what each query saves, 40 CPU-seconds. 1. [ ] 20 queries > 1,200 / (50 + 10) adds the two costs together. The rewrite is paid back by what each query saves, 50 − 10 = 40 CPU-seconds.

Scale up, scale out, or neither? *

Each workload below runs today on one EC2 instance, an m6a.large (2 vCPU, 8 GiB of RAM), unless the row says otherwise. The lecture named these moves for a workload on one instance:

scale up    replace the instance with a larger one
            (more vCPUs, RAM and network on one instance)
scale out   run the work on a cluster of several nodes
neither     keep the one instance as it is
--- shuffle_answers: true --- ## Which scaling move does each workload need? Each option may be used once, more than once, or not at all. - A team of 3 shares a Jupyter environment on the m6a.large and now needs 64 GiB of RAM for a 24 GB dataset :: Scale up > One larger instance gives the team the 64 GiB of RAM, so the 24 GB dataset fits on one instance and no cluster is needed. - Training 100 random forest models with different hyperparameters on a 6 GB dataset takes 12 hours on the largest instance you can get, and the results are needed in 3 hours :: Scale out > The models are independent, so they can run on several nodes at once, and no larger instance is available. Four equivalent nodes with ideal scaling give about 3 hours of run time (12 hours / 4). The 3 hours also include the cluster's launch time, so the team needs more than four nodes. - A dashboard queries a 500 MB SQLite database on the m6a.large :: Neither > The 500 MB database fits in the m6a.large's memory and nothing else in the workload needs more, so a larger instance or a cluster would not help the dashboard. - A weekly report on an m6a.xlarge (16 GiB of RAM) reads 2 of 40 columns from a 7 GB Parquet file and finishes in 20 seconds :: Neither > The reader fetches only the 2 columns it needs, and the report already finishes in seconds, so a larger instance or a cluster would not help the report. - Processing 2 PB of genomic sequencing data from 200 research institutions, which the m6a.large would read through one network link :: Scale out > At the m6a.large's baseline of about 0.78 Gbps, about 97 MB/s, one read of 2 PB takes more than 200 days. A larger instance has a faster network link, but one instance stops at the largest size AWS sells. Each node of a cluster adds its own network link and vCPUs and reads and processes part of the data at the same time. - The m6a.large's 8 GiB of RAM cannot hold a 15 GB Parquet file that a training step needs in memory all at once :: Scale up > The training step needs all of the data in one program's memory at once, and a cluster splits the data across the separate memory of each node, so one larger instance is the move that fits. Parquet files are usually compressed and encoded, so the loaded data takes more than 15 GB: pick an instance with well over 15 GB of RAM. - :: Larger EBS volume > None of these workloads is short of disk space. A volume stores files; it adds no RAM, vCPUs or network.

Terms used on this page

From the course flashcards, grouped by topic. Practise the terms in quiz mode, or try the match game.

Parquet

Parquet. A columnar file format. Rows are grouped into blocks that each store every column separately, and metadata at the end of the file says where each part is.

Row group. A horizontal block inside one Parquet file, holding one column chunk per column. Its size is set when the file is written, and a file can hold one or many.

Column chunk. The values of one field within one row group of a Parquet file. The writer can store their min and max, which lets a reader skip the whole row group.

Footer. The metadata at the end of a Parquet file: the schema, where each column chunk starts and, if the writer stored them, each chunk’s min and max. A reader fetches it before any data.

Projection pushdown. Handing the reader the list of columns a query uses, so it reads only those columns from a Parquet file.

Predicate pushdown. Handing the reader the query’s filter, so it can skip row groups whose stored min and max show that no row can match.

Layout and files on S3

Folder partition. A dataset layout with one named location per value of a column, such as day=2012-06-14/ (on S3, a prefix). A filter on that column skips the other locations without opening them.

Compaction. Rewriting many small files into fewer, larger ones, so a query opens fewer files. Too few files, or too few row groups, can leave cores idle.

Prefix. The leading part of an object’s name, such as day=2012-06-14/. S3 lists objects by it, and the console’s folders are built from it; the general-purpose buckets we use have no real folders.

S3. AWS’s object store. You reach each object over the network by its name inside a bucket, and the data stays with no server running.

Byte-range read. Asking S3 for one stated part of an object instead of the whole object. Parquet libraries fetch the footer this way, then only the column chunks a query needs.

Memory and resources

Eager load. Reading the whole dataset into memory before the work starts. If data and working space exceed memory, the operating system swaps to disk or stops the program.

Storage, memory, compute and network. The four things every data task uses, each with a capacity and a rate. Looking at a job from each in turn helps find its bottleneck, and cloud architecture often trades one for another.

EBS volume. A disk an EC2 instance reaches over the network, as its main disk or an extra one. Its data survives a stop, and it bills per GB-month while it exists, even when the instance is stopped.

Also used on this page

Instance type. The size you pick when you launch an EC2 server: how many vCPUs and how much memory it has, how fast its network is, and whether it has its own local disk.

Time shape of demand. When a workload asks for its resources across a day or a week: a steady rate, a daily rhythm, a burst, or a scheduled job. With the peak rate, it decides whether provisioned or usage-based billing is cheaper.

Amazon EMR. AWS’s managed service that launches a cluster of EC2 instances with Spark installed. You pay for the nodes from launch until you terminate the cluster.

Primary node (EMR). The one EMR instance that runs the cluster manager and the HDFS name service. It runs no executors.

Core node (EMR). An EMR instance that runs executors and stores HDFS data. A role an instance plays in the cluster, not a Spark slot.

Task node (EMR). An optional EMR instance that runs executors and stores no HDFS data, so it can be removed or bought as spot capacity without losing HDFS data.
