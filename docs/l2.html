Object storage: S3

Buoy readings in S3: object names *

An ocean-research lab keeps a year of buoy readings in the S3 bucket buoy-lab, one Parquet object per buoy per day, 200 GB in all. The object keys have the form shown below:

readings/2025-01-01/buoy-04.parquet
readings/2025-01-01/buoy-17.parquet
…
readings/2025-03-01/buoy-04.parquet
readings/2025-03-02/buoy-04.parquet
…
readings/2025-12-31/buoy-17.parquet
--- shuffle_answers: true --- ## Which prefix lists the March 2025 readings and nothing else? 1. [x] `readings/2025-03-` > A prefix is the leading part of an object's key, and it does not have to end at a `/`. Every March 2025 key begins with `readings/2025-03-`, and no other key does. 1. [ ] `readings/2025/03/` > This option treats the keys as folders by year and then by month. A general-purpose bucket has no real folders, and the keys use `2025-03-01`, so no key begins with `readings/2025/03/` and the listing is empty. The console shows prefixes that end in `/` as folders; here those prefixes are `readings/2025-03-01/`, one per day. 1. [ ] `2025-03-` > This option treats a prefix as any part of the key. A prefix is the start of a key. Every key here begins with `readings/`, so no key begins with `2025-03-` and the listing is empty.

Who is responsible for each task, on an instance and on a function?

A team runs the same daily harvest report two ways: on an EC2 instance, a t3a.large running a FastAPI service, and as a Lambda function with a pandas layer and an execution role that can read the bucket vineyard-harvest. These tasks come up over one month.

--- shuffle_answers: true --- ## For each task, who is responsible for it on the instance and on the function? Each option may be used once, more than once, or not at all. - Choosing how much memory the report runs with. :: you on both > On the instance you pick the instance type, and the type fixes the memory together with the vCPUs. On the function you pick one memory setting, and CPU follows that setting. The memory setting fixes the size of each execution environment and is your responsibility; AWS is responsible for the number of execution environments. - Restarting the service after it crashes. :: you on the instance, AWS on the function > On the instance, you run the service, so restarting the service after a crash is your responsibility. On Lambda, AWS is responsible for the execution environment, and the next call runs the function again. - Picking the storage class of the objects in `vineyard-harvest`. :: you on both > The report reads the same S3 bucket on the instance and on the function, and you are responsible for choosing the storage class of the objects in the bucket. - Starting Python and the program that answers requests. :: you on the instance, AWS on the function > On the instance the runtime and the web server (uvicorn for FastAPI) are your responsibility to install and start. On Lambda you supply only the function, and AWS is responsible for starting the runtime. - Shutting the compute down when the day's reports are done. :: you on the instance, AWS on the function > The instance keeps running until you stop it, and you pay for that time. A function runs only while it is called, and AWS is responsible for what happens between calls. - Adding capacity when 200 analysts ask for the report in the same minute. :: you on the instance, AWS on the function > The instance has the capacity of the type you picked, and adding more is your responsibility. On Lambda, scaling to many calls at once is AWS's responsibility. - :: AWS on both > AWS is responsible for the hardware and the hypervisor beneath an EC2 instance. The tasks listed here remain your responsibility on the instance. - :: AWS on the instance, you on the function > This option reverses who is responsible on the instance and on the function. On the instance, AWS is responsible only for the hardware and the virtual machine; you are responsible for the capacity (the type, starting and stopping the instance), the operating system, the runtime, the libraries, the code, the permissions and the security group. On the function, AWS is responsible for the capacity, the operating system and the runtime.

Lambda: a function that runs only when called

Cold starts, warm calls and the memory setting

A Lambda function returns a crop-yield estimate for one field. An execution environment is the isolated space Lambda sets up to run a function, with its memory and a temporary disk; it handles one call at a time and may be reused for later calls. Before its handler runs, the function loads a 60 MB table of soil data from S3 and keeps it in memory. A new version was deployed at 08:55. A call that uses an execution environment that already exists takes about 80 ms; a call that needs a new one takes about 3 s, most of it to load the table. For this question, assume no execution environment exists for the new version before the 09:00 call, that Lambda reuses an idle execution environment when one is available, and that it removes environments that remain idle overnight. These calls arrive:

09:00:00            the first call of the day
09:00:20            after the 09:00:00 call finished, nothing else running
09:00:20 + 50 ms    while the 09:00:20 call is still running
09:00:40            both execution environments idle
07:30 next morning  the first call after no calls all night
--- shuffle_answers: true --- ## For each call, which execution environment does Lambda run it in? Each option may be used once, more than once, or not at all. - the call at 09:00:00 :: new execution environment > The 09:00:00 call has a cold start because no execution environment exists yet for the version deployed at 08:55. Lambda creates a new environment and loads the 60 MB table into it before the handler runs, so the call takes about 3 s. - the call at 09:00:20 :: existing execution environment > The 09:00:20 call is warm: Lambda reuses an existing execution environment. The environment from 09:00:00 is idle, with its soil table still in memory. - the call 50 ms after 09:00:20 :: new execution environment > The call 50 ms after 09:00:20 has a cold start because the environment handling the 09:00:20 call is still busy. Lambda creates a new environment and loads the 60 MB table into it before the handler runs, so the call takes about 3 s. - the call at 09:00:40 :: existing execution environment > The 09:00:40 call is warm because both execution environments are idle then. Lambda uses one of them and reuses its loaded table. - the call at 07:30 the next morning :: new execution environment > The 07:30 call the next morning has a cold start because Lambda has removed the environments that remained idle overnight. Lambda creates a new environment and loads the 60 MB table into it before the handler runs, so the call takes about 3 s. - :: new EC2 instance > Lambda does not start an instance for you. In its standard mode, Lambda creates execution environments on hardware AWS operates, and you never see or pick an instance. - :: same environment, soil table loaded again > An existing execution environment retains the soil table in memory, so a warm call does not repeat the start-up load. Reusing the execution environment explains why the call takes about 80 ms instead of 3 s.

A Lambda function set to 512 MB of memory reads a 40 MB CSV file of field readings and groups it with pandas, which comes from a layer. Each call uses about 300 MB of memory and takes 8 s, with its CPU busy the whole time. The timeout is 30 s.

--- shuffle_answers: true --- ## Which change is likely to make each call finish sooner? 1. [x] Raise the memory setting to 1,769 MB > Lambda's CPU follows the memory setting: 1,769 MB gives one full vCPU, and 512 MB gives less than a third of one vCPU. The CPU is busy for the whole 8 s, so compute is the bottleneck; more memory gives more CPU, and the call finishes sooner, although 300 MB is enough to hold the data. 1. [ ] Pick an instance type with more CPU for the function > This option treats the function as an EC2 instance. A function has no instance type to choose: you pick a memory setting, and CPU follows that setting. 1. [ ] Raise the timeout from 30 s to 60 s > The timeout is the longest a call may run before Lambda stops it. The calls finish in 8 s, well inside 30 s, and a higher limit does not make them faster.

Terms used on this page

From the course flashcards, grouped by topic. Practise them in quiz mode, or try the match game.

EC2 instances

Instance. A virtual machine you rent from AWS, billed per second for the time it runs. Stopping it ends the compute charge, but its EBS disk still bills.

Instance type. The size you pick when you launch an EC2 server: how many vCPUs and how much memory it has, how fast its network is, and whether it has its own local disk.

EBS volume. A disk an EC2 instance reaches over the network, as its main disk or an extra one. Its data survives a stop, and it bills per GB-month while it exists, even when the instance is stopped.

Security group. The rules that say what network traffic may reach an EC2 instance and what it may send out, by protocol, port and address. They do not decide what the instance may do with other AWS resources.

IAM policy. A JSON document that says which actions are allowed on which AWS resources. Attached to a role, it sets what anything using that role may do.

S3

S3. AWS’s object store. You reach each object over the network by its name inside a bucket, and the data stays with no server running.

Bucket. A named container in S3 that holds objects. Its name is part of every object’s address.

Object key. The full name of one stored file inside an S3 bucket. It is only a name, unrelated to the column a group-by or a join uses.

Prefix. The leading part of an object’s name, such as day=2012-06-14/. S3 lists objects by it, and the console’s folders are built from it; the general-purpose buckets we use have no real folders.

Lambda functions

Lambda function. The unit you deploy to AWS Lambda: your code and its settings, run each time a trigger fires. One setting, memory, also sets its CPU and its price per millisecond.

Execution role. The identity AWS takes on when it runs a Lambda function. It decides which resources the code may read or change.

Execution environment. The isolated space AWS sets up to run a Lambda function, with its memory and a temporary disk. AWS may reuse it for later calls and pauses it between them.

Cold start. The set-up before the first call in a new Lambda environment: AWS loads the code, then your code’s initialisation runs, such as opening connections and importing libraries.

Handler. The function in your code that Lambda calls on each invocation, taking event and context. Code outside it runs once per environment, so a client built there is reused.

Billing

Time shape of demand. When a workload asks for its resources across a day or a week: a steady rate, a daily rhythm, a burst, or a scheduled job. With the peak rate, it decides whether provisioned or usage-based billing is cheaper.

Provisioned capacity. Compute you pay for while it is allocated to you, used or not. Unlike pay-per-use compute, its charge continues when nothing runs.

Usage-based billing. Charges for measured work, such as each request or each millisecond a function runs. They stop when nothing runs; stored data and logs still cost money.

Idle test. The question to ask of each compute charge: does it bill while nothing runs? If yes, it is provisioned capacity. Storage and logs are counted separately.
