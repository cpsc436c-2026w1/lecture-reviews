What reaches each copy?

Queue, topic and log: which kind of message broker fits each consumer

--- shuffle_answers: true --- ## A food-delivery app sends order events through AWS and does not store them in a table. For each need, choose the one option that should carry the events, without combining options. Each option may be used once, more than once, or not at all. - Each new order is assigned to one of four kitchen printers :: Queue > A queue, such as Amazon SQS, gives each delivery to one consumer, which deletes the message when it is done. Four printers sharing one queue split the orders between them. A standard queue can deliver a message again, so a printer may see a repeat. A topic with each printer subscribed would copy every order to all four. - A cancelled order must reach the courier app, the customer app and billing as it happens, each its own copy, and none of them reads it again later :: Topic > A topic, such as Amazon SNS, copies each message to every subscriber. On one shared queue, the three consumers would take messages away from each other, and each delivery of a cancel would go to only one of them. A log could also give each consumer every event, but it would keep events that nobody here reads again. - A new fraud model, started today, must also read the orders from the three days before it started :: Log > A log, such as Kinesis Data Streams, keeps every event for its retention period, whether anyone has read it or not. So only a log has events for a consumer that did not exist when they were sent. Kinesis keeps 24 hours by default, so the retention period must already be at least three days when the model starts. A topic does not deliver messages from before the subscription, and a queue does not keep the messages its workers have already deleted. - After a bug, the delivery-time service reads the last two hours again, still within retention :: Log > Reading again is a replay: the consumer moves its offset, its position in the log, back two hours and reads again. A queue's worker deleted each message when it was done, and a topic does not keep anything once delivered. - Ten workers share sending receipts, one receipt per order :: Queue > Each delivery goes to one of the ten workers, which deletes the message when the receipt is sent. The workers share the messages, which DDIA calls load balancing. A redelivery can still send a second receipt, which Q2 deals with. A topic with each worker subscribed would send ten receipts per order. - A refunds service, beside billing and the courier app, wants only the cancelled orders, as they happen, and never reads them again :: Topic > The refunds service is one more subscriber on the topic that carries the cancelled orders, with a filter policy, a rule that passes it only the cancels. Each subscriber still gets its own copy of what it asked for, and nothing has to be kept for later. - :: Nightly export > The app does not store these events in a table, so there is nothing to export, and an export would be a day late for every consumer here. - :: Dual write > The app would write each event once for each consumer itself, and no transaction covers those writes. One write can fail, or two writes can arrive in a different order, so the copies can disagree. A broker takes one write from the producer and serves the consumers from there.

Terms used on this page

Operational system. Reads and changes data as users act.

Analytical system. Holds a read-only copy for analysis.

Polling (L13). The consumer asks the source for new data every T seconds.

Dual write (L13). The application writes the same change to two systems, and no transaction covers both.

Outbox table (L13). A table the application writes each event to, in the same transaction as the change.

Event stream. Unbounded data, made available a piece at a time (DDIA 2e ch. 12).

Event. A record of one thing that happened.

Producer (publisher, sender). The application that makes an event.

Consumer (subscriber, recipient). An application that processes events.

Database trigger. Code the database runs inside each write.

Change stream (L13). A table’s committed changes, read after the write.

Publish/subscribe. Subscribers get what producers send.

Message broker. Holds events between producers and consumers.

Current state. The latest version of each item, as a table keeps it.

Immutable event. A change appended once, never changed.

Partition (AWS: shard). One slice of a stream, in order, with its own read and write limits.

Partition key (Kinesis). The value that picks a record’s shard.

Queue. Each delivery goes to one consumer, which deletes it.

Standard queue (SQS). Delivers each message at least once, in best-effort order.

Load balancing (DDIA). The consumers share the messages.

Acknowledgment. The consumer’s signal that a message is done.

Visibility timeout. How long a queue hides a received message.

SQS FIFO queue. Keeps order within a message group and drops a repeated deduplication id for 5 minutes.

Topic (SNS sense). Every subscriber gets its own copy.

Topic (DDIA, Kafka). A named stream of related events.

Fan-out (DDIA). Each message is delivered to every subscriber.

Filter policy. A subscriber’s rule for which messages it gets.

Log. Events appended in order and kept, read or not.

Log-based message broker (DDIA). A broker that keeps a log.

Offset. A consumer’s position in a log.

Retention period. How long a log keeps each event.

Replay. Move the offset back and read again.

Backpressure. Block the producer until the consumers catch up.

Event sourcing (DDIA 2e ch. 3). The event log is the truth, tables are derived views.

Materialized view. A view built from events, rebuilt by replaying them.

CQRS. Write to the event log, read from forms built per query.

Timeout. The sender stops waiting for an answer after a set time.

Delivery guarantee. How many times each message arrives.

At-most-once. Never retry, so a message may be lost.

At-least-once. Retry until acknowledged, so it may arrive twice.

Effectively-once. At-least-once, plus an effect that counts once.

Idempotent (L12). Applying it twice gives the same result as once.

Request id. An id made where the request starts.

Conditional write (L12). A write that succeeds only if a condition holds.

End-to-end argument. Only the endpoints can provide some functions completely, such as duplicate suppression with a request id from the client to the database (DDIA 2e, ch. 13, “The end-to-end argument”).

Poison message. An event the consumer always fails on.

Dead-letter queue. A queue where failed messages go aside.

On-failure destination. Where Lambda reports a batch it skips.

Event time. When the event happened, by the device’s clock.

Arrival time. When the event entered the stream, by the stream’s clock.

Processing time. When the consumer handles the event.

Clock offset (DDIA). Received time minus sent time, added to the event time.
