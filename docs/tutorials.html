Tutorials

TA-led tutorials. Each entry says what you do in it, which lecture or assignment it supports, and where to find its materials.

Block 2

B2T1: Cluster/EMR

  • What you do: You launch an EMR cluster from the AWS console in your sandbox account, step by step, and check that it starts. You then terminate the cluster so that it stops billing.
  • Supports: L5 (Spark on a cluster) and A2, which runs its Spark job on EMR at two and then four core nodes.
  • Materials: step-by-step guide on Canvas.

B2T2: Spark/Glue

Two parts, each a Glue notebook in the B2T2 repository. Set up your account once with the repository’s step 1 before part A.

A Glue session bills until it stops, even after you close the browser tab. End each notebook with its last cell, %stop_session.

Part A: how Spark reads files

  • What you do: You run the notebook in your sandbox account and see, for each query, which folders, files and row groups Spark reads and how many tasks it starts. Exercises 2 to 6 then ask you to predict those numbers for new queries on the 36 months of taxi trips.
  • Supports: L7 (Spark as a managed service, and its demos on reading files).
  • Materials: the notebook l7a_data-read.ipynb.

Part B: slow queries and their fixes

  • What you do: You run three slow queries from L6 on Glue: input that can’t be split finely enough, a join on a hot key and a window query. Before each run you write down how many tasks you expect, then you read the stage table to find what makes the query slow and which change fixes it. Exercises B1 to B5 follow, with their answers in commented-out cells.
  • Supports: L6 (why a cluster job is slow) and L7.
  • Materials: the notebook l7b_slow-queries.ipynb.

Block 3

B3T1: Lakehouse/Athena+Glue

  • What you do: You query the course’s rides table in Athena, predicting how much each query reads before you run it. You then copy one month into your own account and change it: delete rows, read the table as it was before the delete, load a day twice and repair it, add a column, and join your copy with a course table.
  • Supports: L10 (lakehouses: Iceberg tables, snapshots and time travel) and L11, and the use and change tasks in A3.
  • Before the tutorial: run the one-time setup in the repository’s step 1 (in CloudShell).
  • Materials: the B3T1 repository: the steps, one SQL file per step with the expected results, and the setup script.

B3T2: Lakehouse/Glue build and maintain

  • What you do: You start a ready Glue job that loads one month of rides into an Iceberg table in your own account, and read its script while it runs. You predict how much a query will read from the table’s column sizes, then delete some rows, compact the table with OPTIMIZE, remove old snapshots and their files with VACUUM, and price the job’s run.
  • Supports: L10 and L11 (Iceberg maintenance: compaction, snapshots and VACUUM), and the build and maintain tasks in A3.
  • Before the tutorial: B3T1’s one-time setup, and the B2T2 setup, which creates your bucket and Glue role. Then run the repository’s step 2 in CloudShell.
  • Materials: the B3T2 repository: the steps, one SQL file per step with what to predict, the Glue job and the setup script.

Block 5

B5T1: Course MCP and prompt evaluation

  • What you do: You connect a coding assistant to the course MCP (Model Context Protocol) server and use the course knowledge base to check facts in your project proposal. Then you call the course LLM gateway with the same token and use Inspect, an evaluation tool, to score a prompt on held-out cases (questions kept apart from the ones used to write the prompt). You read and name the failures. Then GEPA, a prompt optimizer, rewrites the prompt. Last, you evaluate the new prompt and work out what the session cost in Canadian dollars (CAD).
  • Supports: L15 to L17 (calling a model, evaluating its answers, the course LLM gateway) and your project proposal.
  • Before the tutorial: do these at home, so the tutorial time goes to the exercises.
    1. Install uv, a Python package manager.
    2. In a terminal on your laptop, clone the tutorial repository with the command in its before the tutorial steps, and clone your team repository. Check that your team repository contains docs/proposal.md.
    3. Install one coding assistant: Claude Code (setup), the Kiro IDE or the Kiro CLI (Kiro installation, IDE tab or CLI tab).
    4. Sign in. For Claude Code, run claude in a terminal. For the Kiro IDE, open Kiro. For the Kiro CLI, run kiro-cli login in a terminal; the Kiro CLI does nothing until you sign in. Kiro accepts Google, GitHub or AWS Builder ID (Kiro authentication).
    5. On GitHub, open the issue “Your course MCP tokens” in your team repository and copy the token next to your name. Set it as the environment variable KB_MCP_TOKEN, as part A, section 2 shows.
  • Materials: Use the B5T1 repository (short link ilm.wiki/436c/b5t1). Part A is in mcp/, and part B is in evals-gepa/.
  • Check your assistant’s connection: after part A’s own check, ask your assistant these two things.
    1. “List what the course MCP server offers: its tools and the kinds of material it has.” A working reply names cpsc436c_search (searches the course material), cpsc436c_read (reads one page in full) and cpsc436c_list (lists the kinds of material, or the pages of one kind), and the kinds: guide, values, dataset, lens and reference. It may also name query_kb, get_kb_doc and list_kb_topics: the same tools under their old names, which keep working until the end of term.
    2. “Use the course MCP server: read the practice lens and run its lens pass on docs/proposal.md.” A working reply is a table with the lens’s two questions (how often each job story happens and how fast its answer is needed; where each number in the data answers comes from), each classified as stated, partial or absent with a quoted line, and then two or three suggestions.
    The wording of the replies changes from run to run. Your model applies the lens; the course MCP server only provides it.
  • Where your assistant shows the connection: in Claude Code, type /mcp in the chat. In the Kiro IDE, open the Kiro panel from the activity bar on the left and find its MCP Servers section. The Kiro CLI has no panel: type /mcp in a kiro-cli chat session. Each lists 436c and aws-knowledge with their connection status.
  • Ask the course server: keep using the assistant you connected in part A. These questions do not ask it to read your team’s files. Ask each separately and check for a course server tool call in each reply.
    1. “What is our AWS budget for the term, and how much can we spend on model calls now? Check with the course server.” A good reply says 30 USD per group lease for the term and about 5 USD of model calls per team for now, more on request for production use, and names the course page for each.
    2. “Which models can our app call through the course LLM gateway, and what is the most output tokens one request may ask for? Check with the course server.” A good reply names qwen3.8-27b and qwen3.6-35b-a3b for chat and qwen3-embedding-0.6b for embeddings, and 16,384 output tokens for one request. It may add the request limit: 120 requests a minute per key.
    3. “We’re thinking of adding retrieval (RAG) to our app. What should we check or read before we decide? Check with the course server.” A good reply names the course readings on retrieval, the course code you can reuse and the course LLM gateway’s limits, each with its course page.
    4. “What can the course server do for us? List what’s available now and what comes later. Check with the course server.” A good reply lists the server’s tools, the current milestone, and the course checks open now and those that open later.
    If a reply has no tool call, ask again: “Check with the course server and show me the tool result you used.”

B5T2: behave and simulated data

  • What you do: You write the step code for one rule of the Checkpoint 1 example with behave, and run it until it passes. Then your coding assistant writes a generator for a simulated data set of your own project (your SIM01), from a small sample of your data and the course’s simulation standards, and a checker tells you whether the set follows them. Last, you run a scenario against a simulated data set, with its expected values taken from the truth files before the run, and find a planted bug from its failing output.
  • Supports: Checkpoint 1 (your features and data set bullets) and Checkpoint 2 (step code that runs against your simulated data sets).
  • Before the tutorial: do these at home, so the tutorial time goes to the exercises.
    1. Install uv, a Python package manager, and git.
    2. Clone the tutorial repository and install its packages with the commands in its before the tutorial steps.
    3. For part B: a coding assistant (Claude Code or Kiro, as in B5T1), and your team repository cloned next to the tutorial repository, with a small sample of your data in it: your data set’s preview file from the project datasets page, or about 20 rows of your own data.
  • Materials: Use the B5T2 repository (short link ilm.wiki/436c/b5t2). The simulation standards are in its docs/simulation-standards.md: they are guidance, not required. Part D, sending a data set to AWS, is for after the tutorial and needs your team’s lease.
