1. Whose job is it, from AWS’s side

--- shuffle_answers: true --- ## In which service is each of these **AWS's** responsibility, not yours? Each option may be used once, more than once, or not at all. - The hardware: the racks and the power :: Both > The provider's floor is the same whatever you rent above it. - The virtual machine layer the code runs on :: Both > An instance is a virtual machine on AWS's hardware, and a function runs in a small virtual machine AWS starts for it. Either way AWS operates that layer. - Patching the operating system :: Lambda > On a function the operating system moved to AWS's side with the runtime and the capacity. On an instance it is yours from the first boot. - Patching the language runtime the code uses :: Lambda > You pick a runtime version from AWS's list and AWS patches it. On an instance you install the runtime, so patching it is yours. - The code that does the work :: Neither > The provider never writes it, whichever way you run it. - The policy that says what your code may touch :: Neither > A role on an instance, an execution role on a function. AWS enforces the policy on both and writes it on neither. - :: EC2 > Nothing AWS runs for you on an instance is missing on a function. On EC2 it runs the bottom two bands; on Lambda those two and three more.

2. Stop or terminate

--- shuffle_answers: true --- ## An EC2 instance was launched with its own volume, left on the default of being deleted when the instance is terminated. A second volume was attached later to hold the data, and that one was set to be kept when the instance is terminated. Each volume is billed for the space it takes while it exists. Which condition does each description below fit? Each option may be used once, more than once, or not at all. - Both volumes are there, and the per-second compute charge is being paid :: Running instance > Nothing has been switched off, so the machine bills and both volumes bill. - Both volumes are there and billing, and no compute charge is being paid :: Stopped instance > Stopping pauses the machine and leaves the storage alone. The storage is what carries on costing. - The launch volume and everything installed on it are kept for the next start, and the compute bill has stopped :: Stopped instance > You pay for the storage over the weekend so that Monday starts where Friday ended. - The launch volume is gone, and the volume attached later is billing on its own :: Terminated instance > The launch volume was set to delete. The attached volume was set to be kept, so it outlives the instance and bills with nothing to show for it. - The launch volume no longer exists, and neither does what was installed on it :: Terminated instance > The launch volume was left on its default, so terminating the instance deleted it along with everything on it. - Somebody is logged in right now, and the compute bill is growing by the second :: Running instance > Billing by the second happens while it runs, whether or not anyone is using it. - :: Instance never launched > Every description here is of a machine that exists and has volumes attached to it.

3. Launch settings for a notebook instance

--- shuffle_answers: true --- ## You launch one EC2 instance to explore a dataset in a Jupyter notebook. The data is 10 GB in a compressed Parquet file in S3. Which launch setting settles each requirement below? Not all options will be used. - Python 3.12 and the AWS CLI must already be in place the first time the machine boots: no install commands may run at all, not even at first boot :: Image > The image is what the machine starts from: its operating system and the software already on it. A user data script could install Python at first boot, but the requirement rules out running any install commands. - Loaded into pandas, the file takes about 30 GB of memory, and the whole DataFrame must fit in memory at once :: Instance type > The type fixes memory, cores and network. Disk space doesn't help: a DataFrame is held in memory, and the file itself stays in S3. - AWS lets connections reach the machine only on port 8888, and only from your own IP address :: Security group > It decides which ports are reachable from which addresses. It does not check who you are, or decide what the machine may read in S3. - The notebook reads the file from S3 without anyone putting access keys in a file on the machine :: Role > An EC2 instance can be given a role. Its policy says what the instance may read, so no one has to paste access keys into a file on the machine. - :: User data script > Commands the machine runs at first boot. Here everything needed is either in the image or set by another setting. - :: Volume size > It sets disk space, not memory, and the file is read from S3, not stored on the disk.

4. A function or an instance

--- shuffle_answers: true --- ## Which fits each piece of work best? Each option may be used once, more than once, or not at all. - A file of a few MB lands in an S3 bucket a few times an hour and needs a few seconds of work to convert :: A function > Short, started by an event, and idle most of the hour. No compute runs or is paid for between arrivals. - A model fit on a 2 GB table that takes forty minutes, cannot be broken into shorter steps, and runs once a night :: An EC2 instance > One call of a function stops at fifteen minutes, and this job cannot be split into calls that fit. A machine started for the job and stopped after it is the shape left, and the table fits in its memory. - Someone working in a notebook all afternoon on a 5 GB table, changing code and re-running it :: An EC2 instance > The session has to stay up between keystrokes, and the data in memory has to survive from one cell to the next. Saving files between calls moves the files, not the session. - A web endpoint answering a few short requests a minute, at all hours, where a second's delay now and then is fine :: A function > Almost always idle, and each request is short. The bill follows the requests, not the hours. - A daily summary of yesterday's 200 MB that takes two minutes and writes one file :: A function > Short, scheduled and rare. A machine kept for it would sit idle for the rest of the day. - :: A cluster of several machines > Every workload here fits on one machine, in its memory and in its time. Spreading work over several machines pays only when one cannot do it.

5. What starts the function

--- shuffle_answers: true --- ## A smart-home company runs several functions. What starts the function in each situation below? Each option may be used once, more than once, or not at all. - Someone asks the voice assistant "what is the temperature?" and it answers a second later :: Request > Someone is waiting for the reply: a request starts the function and gets the answer back. - A thermostat writes a new reading file to a bucket, and a function checks whether it is outside the safe range :: Event > The new file is the event; its arrival starts the function. Nobody waits for the check. - A new firmware file is uploaded to a bucket, and a function checks its signature :: Event > The upload is the event; a rule sends it to the function. Nobody waits for the result. - A new recording from a door camera lands in a bucket, and a function blurs the faces in it :: Event > The recording's arrival is the event; a rule sends it to the function. Nobody waits for the result. - Every night at 03:00 a function deletes test devices' logs older than a week :: Schedule > A clock starts it. - On the first day of each month a function totals each household's energy use :: Schedule > A fixed date on the calendar: a schedule. - :: Deployment > Deploying a new version puts the code in place. It does not run until a request, an event or a schedule starts it.

6. Why the Parquet read is small

--- shuffle_answers: true --- ## A city keeps three years of bike-share rides in S3 as Parquet, already compressed, 4.2 GB, sorted by start time, in 60 row groups. A query asks for the average ride duration per station in March 2025, which needs one month and 3 of the file's 14 columns. Run with DuckDB against the Parquet copy, it reads 35 MB from S3. What explains the reduction from 4.2 GB to 35 MB? 1. [x] The 11 unneeded columns are never fetched, and the footer's statistics rule out row groups that cannot match > Two savings at once. Each column's bytes are stored apart, so the 11 unneeded columns are never read, and the minimum and maximum start time per row group rule out every group outside March 2025. 1. [ ] S3 applies the filter inside the bucket and returns only the rows that match > In this DuckDB run, S3 returns the requested byte ranges; it does not run the query. The reader reads the footer, decides which byte ranges it needs, and asks for those. 1. [ ] The data is compressed on the way across the network, so far fewer bytes have to travel > The 4.2 GB is already the compressed size. The reduction comes from not reading most of the file at all. 1. [ ] The whole file is fetched and the unwanted parts are dropped once it arrives > That would move all 4.2 GB. The reader fetches the footer first, which says where each column and row group sits and the minimum and maximum in each, then asks only for the byte ranges it needs.

7. Where the S3 client is made

--- shuffle_answers: true --- ## A Lambda function, with default settings, has the line `s3 = boto3.client("s3")` as the first line of its handler, then uses the client to write one small file. A hundred calls arrive in a minute, one after another, and one execution environment serves them all. Which statement is true? 1. [x] The client is created on every call > Everything inside the handler runs on every call. Code at module level runs once, when the environment starts, and the calls after that reuse what it made. 1. [ ] The client is created once, because Lambda keeps objects made inside the handler between calls > A local made in the handler is gone when the call returns; only what module level made is there for the next call. 1. [ ] The client is created once, when the code is deployed > Deploying puts the code in place. None of it runs until an environment starts to serve a call. 1. [ ] The client is created once, when the environment starts, as if the line were at module level > The line is inside the handler, so it runs when the handler runs: on every call. Only code outside the handler runs when the environment starts.

8. Function, instance or cluster

--- shuffle_answers: true --- ## Which way of running it fits each piece of work best? Each option may be used once, more than once, or not at all. - A mobile app asks, a few times a minute, for the nearest open store; each answer takes 200 ms to compute :: A Lambda function > A short answer to a request, with nothing to keep running between requests. - Every hour an EventBridge schedule starts a check that a website answers, which takes a second :: A Lambda function > A short task on a schedule, with nothing to keep running between checks. - A model is trained on a 3 GB table for two hours in one Python process, after which the machine is not needed :: One EC2 instance > One process on one machine, far longer than a function may run, and nothing to stop afterwards but the instance. - A FastAPI app on port 8000 loads a 2 GB table when it starts and answers `/summary` requests all day :: One EC2 instance > A process that stays up and holds state; one machine holds 2 GB. - A Spark job on 3 TB needs a node type with a lot of memory that the team picks itself :: An EMR cluster you start and stop > Too big for one machine, and the team wants to choose the nodes' instance type, which an EMR cluster lets it do. - Ten analysts share Spark notebooks on one cluster all week, with node types the team chose :: An EMR cluster you start and stop > A cluster kept up for many notebooks, on nodes the team picked: EMR on EC2. - :: An AWS Glue job > On Glue the workers last for one job and nobody picks machines. Every Spark row here needs chosen node types or a cluster that stays up all week.

9. What Spark can skip

--- shuffle_answers: true --- ## A scooter-share company keeps its trips as Parquet in S3, in one folder for each trip date: `trip_date=2025-07-01/`, `trip_date=2025-07-02/`, and so on. Each folder holds one file, sorted by scooter id, with about 10 row groups. Each row group's footer records the minimum and maximum of each column, and Spark can use them. Which data can Spark skip for each condition? Each option may be used once, more than once, or not at all. - `WHERE trip_date = '2025-07-14' AND scooter_id = 'SC-0417'` :: Whole folders and row groups > The date names one folder, so the others are skipped. Inside that day's file, sorted by scooter id, the footers rule out the row groups that cannot hold SC-0417. - `WHERE trip_date IN ('2025-07-14', '2025-07-15')` :: Whole folders > Two folders match by name, and all the others are skipped. Inside them every row is needed. - `WHERE scooter_id BETWEEN 'SC-0400' AND 'SC-0499'` :: Only row groups inside the files > The condition does not name the folder column, so every day's folder is opened. Each file is sorted by scooter id, so the footers rule out the row groups outside that range. - `WHERE scooter_id = 'SC-0417' AND battery_end < 10`. Every row group has some trips that ended below 10% battery :: Only row groups inside the files > The scooter id rules out row groups in every file. The battery condition rules out nothing. - `WHERE trip_date = '2025-07-14' AND battery_end < 10`. Every row group has some trips that ended below 10% battery :: Whole folders > The date skips the other folders. Inside that day's file the battery condition rules out no row group. - `WHERE battery_end < 10 AND city = 'Vancouver'`. Every row group has trips from every city, some below 10% battery :: Neither folders nor row groups > Neither column names the folders, and every row group holds both kinds of trip. - :: In S3, the rows that do not match > S3 hands back the byte ranges Spark asks for. Spark decides what to skip, from folder names and footers.

10. What happens when each line runs

--- shuffle_answers: true --- ## In a PySpark notebook on an EMR cluster, `recent` is a Spark DataFrame of 2025's ticket sales made from Parquet files in S3, `pd` is pandas, and `F` is `pyspark.sql.functions`. What happens when each line runs? Each option may be used once, more than once, or not at all. - `venues_pd = pd.read_parquet("s3://tickets-raw/venues.parquet")` :: pandas does the work in the driver only, with no Spark plan > This is pandas: it runs in the driver's process alone. - `large_pd = venues_pd[venues_pd["seats"] > 1000]` :: pandas does the work in the driver only, with no Spark plan > This is pandas filtering in the driver: no Spark plan, no tasks. - `avg_seats = venues_pd["seats"].mean()` :: pandas does the work in the driver only, with no Spark plan > Still pandas on the driver: no plan, no tasks. - `by_price = recent.orderBy(F.col("price").desc())` :: Spark adds a step to the plan. No task starts > A sort is a transformation too: it goes into the plan and waits for an action. - `n = recent.count()` :: Tasks start on the executors > Counting is an action: the plan runs and the number comes back to the driver. - `recent_pd = recent.toPandas()` :: Tasks start on the executors > toPandas is an action: tasks read and filter on the executors, then every row is sent to the driver. - :: S3 filters the rows before they come to Spark > S3 returns the bytes it is asked for. Filters run in Spark's tasks, or in pandas on the driver.

11. Where each thing is kept

The cluster is terminated at the end of the day. Where is each thing below kept while the notebook runs? Each option may be used once, more than once, or not at all. - The 300 depot totals, turned into a pandas DataFrame with toPandas() to draw a chart in the notebook :: In the memory of the driver > toPandas() brings the rows back from the executors into one pandas DataFrame, in the driver's process. - A small list of depot names read with pd.read_csv in the notebook :: In the memory of the driver > This is pandas, not Spark: it runs in the driver alone and keeps its DataFrame there. - Files an earlier job saved on the cluster's HDFS for a later job on the same cluster :: On the disk of a node > HDFS keeps its blocks on the core nodes' disks, and they go when the cluster does. - A temporary file a task creates in its node's local folder and deletes before the task ends :: On the disk of a node > A task's own scratch file sits on the node that runs it. - A public Parquet dataset that several teams' clusters read :: In an S3 bucket > Shared by many clusters and kept after each one ends: S3. - A results file a teammate opens next week, after this cluster is terminated :: In an S3 bucket > The cluster's disks go with it, so anything needed later goes to S3. - :: In the Glue Data Catalog > The catalog keeps table definitions, the metadata, not the rows. None of these is a table definition.

12. Fewer slots

--- shuffle_answers: true --- ## To save money, a cluster shrinks from 2 core nodes to 1, so from 8 slots to 4. In one scan stage, 12 tasks read rows, and each takes about the same time. A task starts when a slot is free, and nothing else changes. How does the stage's time change? 1. [x] It grows to about one and a half times the old time > On 8 slots, 12 tasks run in two waves: 8, then 4. On 4 slots they run in three waves of 4. 1. [ ] It grows to about twice the old time > Half the slots does not mean twice the waves. Count them: two before, three after. 1. [ ] It grows to about three times the old time > Three is the number of waves on 4 slots, not how much longer the stage takes. Before, it took two. 1. [ ] It stays about the same > With 4 slots, 4 of the 12 tasks now wait for a free slot, so a third wave is added.

13. Row groups and tasks

--- shuffle_answers: true --- ## A 230 MB Parquet file holds 6 row groups of about the same size. The cluster grows from 8 slots to 16, and Spark's scan of the file now makes 16 tasks. How many of those tasks read rows? 1. [x] 6: only the ranges that hold a row group's middle read rows > Spark cuts the file into about 16 byte ranges. Spark never divides a row group between ranges; one range reads each of the 6 row groups. 1. [ ] 16: each task reads half of a row group > A row group is never split between tasks. The task whose range holds its middle reads all of it. 1. [ ] 1: only the first task reads rows > That is what a file with one row group does. Here there are 6 middles, spread across the file. 1. [ ] 16: each range reads every row group it overlaps > A row group goes to one range only, the one that holds its middle, so nothing is read twice.

14. Nodes for a deadline

--- shuffle_answers: true --- ## A mapping company must render 2,400 satellite image tiles on an EMR cluster before the morning. The tiles are independent of each other, and each takes 5 minutes on one vCPU. They can be spread over any number of vCPUs with no overhead. The cluster has one primary node, which renders nothing, plus core nodes of type m6a.xlarge, each with 4 vCPUs for rendering. Launch takes 10 minutes before the first tile can start, and everything must finish 4 hours after the cluster starts, launch included. Step 1: how much work is it, in vCPU-hours? 1. [x] 200 > 2,400 tiles × 5 minutes is 12,000 vCPU-minutes, which is 200 vCPU-hours. 1. [ ] 12,000 > That is the work in vCPU-minutes. Divided by 60 it is 200 vCPU-hours. 1. [ ] 2,400 > That is the number of tiles. Each one is 5 minutes of one vCPU's work. 1. [ ] 50 > That divides by the 4 vCPUs of a node, which gives node-hours, not the work itself. ## Step 2: what is the smallest number of core nodes that finishes in time? 1. [x] 14 > After the 10-minute launch, 3 hours 50 minutes are left. 200 vCPU-hours over about 3.83 hours needs about 52.2 vCPUs at once: 53, which is 13.25 nodes, so 14. 1. [ ] 13 > Thirteen nodes give 52 vCPUs, and 200 vCPU-hours over 52 vCPUs takes about 3 hours 51 minutes: just over the 3 hours 50 minutes left once the 10-minute launch is taken out. 1. [ ] 15 > Fourteen nodes already give 56 vCPUs, more than the 53 needed. 1. [ ] 50 > 200 vCPU-hours divided by 4 vCPUs per node is a number of node-hours, not of nodes. It still has to be spread over the hours left.

15. Choosing the folder key

--- shuffle_answers: true --- ## A delivery company keeps three years of parcel scans in S3 as Parquet, about 200 GB a year. Each row is one scan: the scan time, the depot (300 depots), the parcel id (80 million parcels) and the status. Each week an audit job reads all three years of scans at one depot, a different depot each week. Which folder key lets that job skip all the other data, while keeping the number of folders small and each folder large? 1. [x] Depot > The job reads one depot's folder and skips the other 299. Three years over 300 depots is about 2 GB a folder. 1. [ ] Scan date > Every date folder holds scans from every depot, so the job would have to open all of them. 1. [ ] Scan hour > The same problem as the date, and about 26,000 small folders on top of it. 1. [ ] Parcel id > 80 million folders of a few rows each, and nothing in the name says which depot a parcel passed through.

16. Why the stage is slow

--- shuffle_answers: true --- ## After an Exchange by store, a stage runs 200 tasks. The median task takes 0.3 seconds on about 50 thousand rows; one task takes 40 seconds on 9 million rows. What is the most likely cause of the slow stage? 1. [x] One key has many more rows than the others > Every row with the same key goes to the same task after the Exchange, so a store with far more rows than the others lands all of them on one task. 1. [ ] The rows each task holds do not fit in the memory available to that task > Memory per task is the same for all 200 tasks. One task forty times the median points to what that task holds, not to how much memory each task has. 1. [ ] Too few readable parts of the input > That shows up in a scan stage, as tasks that read no rows. This stage comes after an Exchange. 1. [ ] Too many small files and folders > Small files slow down listing and the start of a scan. They do not make one task after an Exchange forty times the others.

17. What the team chooses on EMR

--- shuffle_answers: true --- ## A team moves a nightly PySpark job from an AWS Glue job to an EMR cluster on EC2. On EMR, what does the team now choose that it did not choose on Glue? 1. [x] The EC2 instance type of each node > On EMR the team rents nodes and picks their instance types. On Glue there were no machines to pick. 1. [ ] The Spark version the job runs on > Both fix it: the EMR release on EMR, the Glue version on Glue. 1. [ ] The PySpark code of the job > The team writes the code on both.
