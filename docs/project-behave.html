Behave for your project

behave is a Python tool that runs tests written as plain-text examples. In your project, each example shows one requirement or one constraint (RF ID) of your system with data and a known answer. This page takes you from a first draft to tests that run against your system on AWS. You need only the level that your checkpoint asks for.

Level When you need it What you do
Level 0 Checkpoint 1 Write draft rules and examples, and check them with a dry run. You do not write code.
Level 1 Checkpoint 2 (proposed) Write the Python function behind each step, and run the examples.
Level 2 Later (proposed) Use ready steps from the course kit for the simulator, DuckDB queries and evals (runs of a model’s answers on cases with known answers).
Level 3 Later (proposed) Run chosen examples on AWS, and make an eval a gate: an example that fails when fewer runs are correct than the number you chose.

Levels 1 to 3 are proposed and may change before Checkpoint 2.

The examples on this page come from the rides example of the Checkpoint 1 page: a ride-hailing app in New York whose trip events (a trip is requested, accepted, completed) reach the system of a team t00. The whole example is the repository cp1-example, tag cp1. Run the Level 0, Level 2 and Level 3 commands in a terminal at the root of your repository. The Level 1 example has a folder of its own, and its steps say where to work. The outputs on this page come from behave 1.3.3, and every command pins that version (uvx behave@1.3.3) because older versions do not read Rule:: behave 1.2.6 stops with a ParserError at the first Rule: line.

Level 0 (Checkpoint 1): draft rules and examples without code

At this level you write files in Gherkin, the plain-text format that behave reads, and check that behave can read them, before any Python code exists. Each file is a feature file: its name ends in .feature, and it holds one Feature:. In it:

  • a rule (Rule:) states one requirement, and carries its ID as a tag;
  • an example (Example:) under a rule shows the rule with data and an answer that you know before the system runs. Example: is another word for Scenario:, and behave’s output says “scenario”;
  • an example is written as steps: lines that start with Given, When, Then, And or But. The Given sets up the data and the state before, the When is the event or the question, and the Then is what must be true after (behave: Given, When, Then).

Examples: with an s is a different thing: the table of a Scenario Outline.

Folder layout

behave looks for a folder named features/ at the root of your repository, and inside it for a folder named steps/ (behave: feature testing layout). The steps/ folder holds Python files at Level 1. At Level 0 it holds one empty file, so that git keeps the folder.

  1. Create both folders and the empty file:

    mkdir -p features/steps
touch features/steps/.gitkeep

  2. Check the result with ls -a features features/steps. You should see steps in the first list and .gitkeep in the second.

When your feature files are written, the layout of the rides example is:

features/
├── js01_trips_per_zone.feature     serves JS01
├── js01_yesterdays_trips.feature   serves JS01
├── js04_pickup_place.feature       serves JS04, with the assistant
├── trip_assignment.feature         serves JS02 and JS03
└── steps/
    ├── .gitkeep                    empty at Level 0
    └── pickup_steps.py             in the example only (see the dry run below)

Job stories and feature files

A job story can need more than one feature file, and one feature file can serve more than one job story:

  • By default, write one feature file for each job story you plan to implement, named for what the user gets, and tag its Feature: with the story’s ID (@JS01).
  • Split a story into two feature files when the user gets two different things from it. Each feature’s description says which part of the story it covers. In the example, the analyst of JS01 gets the trips requested in each zone and, each morning, yesterday’s completed trips: two feature files.
  • Share a feature file between two stories when both users read the same thing. It carries both tags (@JS02 @JS03), and a requirement that both stories share has its rule once, in that feature file. In the example, the driver (JS02) and the rider (JS03) read the same assignment of a trip to a driver.
  • A story tag on a feature says that every rule in it serves that story. When one rule serves one more story, put that story’s tag on the rule.

A feature file named “Constraints”, or after an ID, does not name anything a user gets. Put the rule of each RF in the feature file of the job story that the constraint is about.

One rule for each ID

Each R ID in docs/requirements.md, and each RF ID whose line ends with a [Scenario](…) link, gets one Rule: in one feature file, tagged with its ID: @R020 for your own requirement R020, @RF010 for the constraint RF010 of your proposal feedback issue. Under the rule goes at least one Example:. RQ IDs, and RF IDs whose line ends with Read: or Read at Checkpoint 2:, do not get a rule.

  1. Create features/js01_trips_per_zone.feature, or use a file name that fits your story. You should see the file in features/.
  2. Put the story’s tag, Feature: with a name, and a sentence on what part of the story the feature covers. behave does not run this text: it is there for the person who reads the file.
  3. Add one rule with its ID as a tag, and one example under it, as shown below, and save the file. Indent the lines as shown, with spaces. The table’s columns are fields of a trip request: event_id is one ID for one event, trip_id is one ID for one trip, pickup_zone_id is the zone the rider is in, event_time is when the rider asked, and received_time is when the event reached the system.

The file below is a shortened version of the example’s features/js01_trips_per_zone.feature: two lines of its description, and one of the three examples of its rule for R020.

@JS01
Feature: Trips requested in each zone
  Covers the first part of JS01 (operations analyst): the number of trips requested in each pickup zone for each
  5-minute period. A period holds the requests with an event time from its start up to, and not including, its end.

  @R020
  Rule: If a request is received after its period ended, then the system shall add it to the stored count of the period of its event time, and store a count of 1 if its zone does not have a count for that period yet

    Example: Request received 7 minutes late
      Given only these trip requests are received:
        | event_id  | trip_id | pickup_zone_id | event_time           | received_time        |
        | ev-000011 | t-0011  | 161            | 2026-11-23T09:01:10Z | 2026-11-23T09:01:11Z |
        | ev-000012 | t-0012  | 161            | 2026-11-23T09:04:00Z | 2026-11-23T09:11:00Z |
      When the time is 2026-11-23T09:11:30Z
      Then zone 161 has 2 trips requested between 09:00 and 09:05

The rule is the requirement R020 of docs/requirements.md in sentence case: it says what the system shall do. The example’s answer, 2, follows from its table: request ev-000012 has an event time of 09:04, inside the period from 09:00 to 09:05, and was received 7 minutes later, at 09:11. The When is 30 s after that receipt, inside R020’s target of data latency under 60 s at p95 for a late request; one example checks one such request.

Tags

@JS01, @R020 and @RF010 are tags: labels that start with @, on the line above a feature, a rule or an example. A tag reaches everything under it: the examples of a rule carry the rule’s tag, and every example of a feature carries the feature’s tag. To dry-run only the examples of one ID, name its tag: uvx behave@1.3.3 --dry-run --tags=R020 (behave: tag expressions).

When one of your own requirements is how you meet an RF, write one rule with both tags. In the example, R080 (refuse the second accept of a trip) meets RF030 (two drivers accept the same trip at the same moment), so its rule is tagged @R080 @RF030.

@RF010 above a rule is a tag: a label that --tags selects and reports show. @given above a Python function (Level 1) is a decorator: it makes the function a step.

behave gives special meaning to only a few tags: @wip when you run behave --wip (behave: works in progress), and tags that start with @fixture. or active tags such as @use.with_, but only when features/environment.py sets them up (behave: tags in Python, behave: active tags). ID tags such as @R010 and @RF010 are plain labels, and so are @eval and @live at this level.

From an EARS line to a rule and its examples

Each R line of docs/requirements.md is written in EARS form: an optional opening such as WHEN <trigger>, then THE SYSTEM SHALL and what the system does. The form says where each part goes in the example:

EARS form In the example
WHEN <trigger> THE SYSTEM SHALL <response> the trigger is the When, the response is the Then, and the Given holds the data before
WHILE <state> THE SYSTEM SHALL <response> the state is in the Given (the data) and the time of the When; the response is the Then. An example shows one moment of the state
IF <problem> THEN THE SYSTEM SHALL <response> the problem is an injected fault in the Given (the same event_id twice, a late received_time); when the problem is the request itself, such as a value out of range, it is the When
THE SYSTEM SHALL <response> the rule’s sentence is the requirement; choose two examples that differ in something that could break it
WHERE <feature> THE SYSTEM SHALL <response> a tag on the feature that names the option, such as @assistant
the target after \| (data latency under 60 s at p95) one case of it in the Then (“within 30 s”, inside the target), or a time in the When chosen so that the answer must already hold; the percentile needs many cases

Write each Rule: line with the EARS form and meaning of its R line, in sentence case, so that it says what the system shall do (When a 5-minute period ends, the system shall store one count …); an RF line becomes The system shall …. Name only the situation in an Example: title and leave the outcome to its Then: not A request at the end of a period is in the next period, but A request exactly at the end of a period (09:05:00).

The answer of an example (2 trips) is not a requirement; the target from the R line (data latency under 60 s at p95) is. The times in an example are data: nobody waits for them.

Data in an example

An example gets its data from a table inside it or from a simulated data set:

  • A table inside the example, for a few hand-picked events. Its columns are the fields of the event, as the event fields of the ## Data section of your docs/design.md list them, and the first row holds their names. Use it when 2 or 3 events show the rule, as in the R020 example above. The word “only” in Given only these trip requests are received says that the table holds all the requests of the example.
  • A simulated data set, for the cases where the number of events matters, such as a whole hour or a whole file: events or files that your team will generate from a real data set, so that a test knows every event that was sent. Name it by its ID and name: Given the simulated data set SIM01 "rush-hour". At Checkpoint 1 the data set is a bullet of words in the ## Data section; its example is read by the dry run like any other.
    Example: One simulated hour with 4 requests delivered twice
      Given the simulated data set SIM01 "rush-hour"
      When the counts are read at 2026-11-23T10:11:00Z
      Then zones 48, 161 and 230 show 304, 191 and 342 trips requested between 09:00 and 10:00

Put the data of each example in the example itself, not in a Background: a reader then sees the data and the answer together.

How to write a good example

Describe what the system must do, not what a person clicks

An example stays true when you change a page or rename a button. Write the data in the Given, the one event or question in the When, and the result that a user or another system can observe in the Then (behave: Then).

This example describes clicks, and its Then does not have anything that a test can compare:

    Example: Check the counts
      Given I open the dashboard and click "Refresh"
      When I wait for the page to load
      Then the counts look right

This example describes the same requirement as behaviour:

    Example: One request delivered twice
      Given only these trip requests are received:
        | event_id  | trip_id | pickup_zone_id | event_time           | received_time        |
        | ev-000101 | t-0101  | 161            | 2026-11-23T09:11:00Z | 2026-11-23T09:11:01Z |
        | ev-000102 | t-0102  | 161            | 2026-11-23T09:12:30Z | 2026-11-23T09:12:31Z |
        | ev-000101 | t-0101  | 161            | 2026-11-23T09:11:00Z | 2026-11-23T09:12:40Z |
      When the counts are read at 2026-11-23T09:15:30Z
      Then zone 161 shows 2 trips requested between 09:10 and 09:15

Show one behaviour in each example

Test one behaviour in each example, as the behave documentation recommends (behave: scenarios): when the example fails, its name tells you which situation broke it. If an example checks two unrelated outcomes, split it into two examples, under the rules they show.

Put a number or a fixed answer in the Then

The Then compares what the system produced with an answer that is known before the run. You chose the data, so you know the answer: the table above holds two different event_id values, so 2 must be counted.

Then that a test cannot check Then with a number or a fixed answer
Then the counts look right Then zone 161 shows 2 trips requested between 09:10 and 09:15
Then the quiet zone is handled Then zone 48 shows no data between 09:25 and 09:30
Then the late request is handled Then zone 161 has 2 trips requested between 09:00 and 09:05

Testing model answers

A model’s answer can differ between runs, so one example with a fixed reply does not show a requirement on it. An eval runs the model’s part of your system on a set of cases with known answers, each case several times, and counts the runs with a correct answer. The rule gets one gate example: an example tagged @eval whose steps name the eval of your ## Evals section in docs/requirements.md, its number of cases, the runs of each case, and how many runs must be correct; it fails when fewer runs are correct. Beside it go ordinary examples, each with one input and the answer that the rule allows, such as a message that names only a destination.

@JS04 @assistant
Feature: Pickup place of a rider's message
  Covers JS04 (support agent) in a system that includes the assistant, our extension. The assistant sends the
  rider's message to the model as the user message; the output format is a JSON object with one field,
  pickup_place: a name from evals/pickup_place/places.txt, null when the message names no pickup place, or
  "more than one" when it names more than one.
  Step code: this example repository has step code for this feature only, to show how an LLM eval runs in behave.
  You do not write step code for Checkpoint 1.

  @R110
  Rule: Where the system includes the assistant, when a support agent opens a rider's message, the system shall show the pickup place that the message names, as a name from our list of places, or say that the message names no pickup place

    Example: Message that names a pickup place
      Given the rider message "I'm waiting outside JFK Terminal 4, door 6. Where is my driver?"
      When the support agent opens the message
      Then the pickup place is "JFK Terminal 4"

    Example: Message that names only a destination
      Given the rider message "Take me to Penn Station. I haven't decided where to be picked up yet."
      When the support agent opens the message
      Then the system says that the message names no pickup place

    @eval
    Example: Eval of pickup places
      Given the 10 cases of the eval "pickup-place"
      When the model that the system uses answers each case 3 times
      Then the pickup place is correct in at least 24 of the 30 runs

  @R120
  Rule: If a rider's message names more than one pickup place, then the system shall say that the message names more than one pickup place, and not show any of them as the pickup place

    Example: Message that names two pickup places
      Given the rider message "Pick me up at Penn Station or at Grand Central Terminal, whichever is faster for the driver."
      When the support agent opens the message
      Then the system says that the message names more than one pickup place

Level 1 (Checkpoint 2, proposed): a first step function

TipPractise it in tutorial B5T2

Tutorial B5T2 (repository) walks through this level on the rides example: you write three step functions by hand, have your coding assistant write the steps of a second rule and check them, then run a scenario on a simulated data set whose expected value comes from its truth. After the section, B5 makes a simulated data set for your own project.

At this level you write the Python code that makes each step do something. A step function is a Python function that behave calls when it reaches a step with a matching text. Build the example below once in an empty folder outside your repository, then do the same for your own scenarios.

The example tests one small function, count_requests, with a scenario of four steps. To stay short, it puts the tag @RF010 on a Scenario: without a Rule:; in your repository, your examples stay under the rules of their IDs. The example has these files:

behave-first-step/
├── rides.py                     the code under test
└── features/
    ├── request_counts.feature   the scenario
    ├── environment.py           setup and teardown
    └── steps/
        └── request_steps.py     the step functions

Code under test and its scenario

  1. In a terminal, move to the folder that holds your repository’s folder (cd .. from the root of your repository). Create the example folder there and move into it:

    mkdir -p behave-first-step/features/steps
cd behave-first-step
pwd

    You should see a path that ends in /behave-first-step. Run every command of this level in this folder.

  2. Create rides.py with the code below. The function reads a file with one trip request on each line and counts the requests of each pickup zone. A request that arrives twice has the same event_id both times, and the function skips an event_id it has already seen. After you save the file, run ls rides.py. You should see rides.py listed.

    import json


def count_requests(path):
    seen = set()
    counts = {}
    for line in open(path):
        request = json.loads(line)
        if request["event_id"] in seen:
            continue
        seen.add(request["event_id"])
        zone = request["pickup_zone_id"]
        counts[zone] = counts.get(zone, 0) + 1
    return counts

  3. Create features/request_counts.feature with the scenario below. After you save it, run ls features/request_counts.feature. You should see the file listed.

    @JS01
Feature: Trips requested in each zone
  When demand moves between zones, I want the number of trips requested in each
  pickup zone, so that I can send free drivers where the requests are.

  @RF010
  Scenario: A request that arrives twice
    Given riders in zone 161 request 6 trips
    And the simulator delivers 2 of the requests a second time
    When the requests are counted
    Then zone 161 has 6 trips requested

    A step that starts with And continues the kind of step above it (behave: And, But). Here the And line is a second Given.

Setup and teardown in environment.py

Some work belongs to every scenario and to none of its steps: creating an empty folder or table before the scenario, and removing it after. behave reads a file features/environment.py and calls the functions in it that have fixed names, called hooks: before_scenario runs before each scenario and after_scenario runs after it. There are also before_all, after_all, before_feature and after_feature (behave: environmental controls).

Every hook and every step function receives context as its first argument. context is an object on which you store what a later step needs, as attributes: context.requests_file = .... behave empties it of the values of a scenario when the scenario ends, so one scenario does not see the data of another (behave: context).

  1. Create features/environment.py with the two hooks below. After you save it, run ls features/environment.py. You should see the file listed.

    import tempfile
from pathlib import Path


def before_scenario(context, scenario):
    # Setup: every scenario gets an empty folder of its own for the requests file.
    context.folder = tempfile.TemporaryDirectory()
    context.requests_file = Path(context.folder.name) / "requests.jsonl"


def after_scenario(context, scenario):
    # Teardown: runs after the scenario, also when a step failed.
    context.folder.cleanup()

Step functions with parameters

A step function has a decorator, @given, @when or @then, with the text of the step. A part of the text in curly brackets is a parameter: behave takes the value from the scenario’s line and passes it to the function as an argument. {name} gives text, and {n:d} gives a whole number (behave: step parameters). One function then serves every scenario that uses the same sentence with other values.

  1. Create features/steps/request_steps.py with the code below. The file name is your choice: behave loads every .py file in features/steps/ (behave: Python step implementations). After you save it, run ls features/steps/request_steps.py. You should see the file listed.

    import json

from behave import given, then, when

from rides import count_requests


@given("riders in zone {zone:d} request {n:d} trips")
def step_riders_request(context, zone, n):
    context.requests = [
        {"event_id": f"ev-{i:06d}", "pickup_zone_id": zone} for i in range(n)
    ]
    _write(context)


@given("the simulator delivers {n:d} of the requests a second time")
def step_delivered_twice(context, n):
    context.requests += context.requests[:n]
    _write(context)


@when("the requests are counted")
def step_count(context):
    context.counts = count_requests(context.requests_file)


@then("zone {zone:d} has {n:d} trips requested")
def step_check_count(context, zone, n):
    actual = context.counts[zone]
    assert actual == n, f"zone {zone}: expected {n}, actual {actual}"


def _write(context):
    lines = [json.dumps(request) for request in context.requests]
    context.requests_file.write_text("\n".join(lines) + "\n")

    Read the four functions against the four steps of the scenario:

    Step in the scenario Function What it does
    Given riders in zone 161 request 6 trips step_riders_request(context, 161, 6) Writes 6 requests into the file that the setup named.
    And the simulator delivers 2 of the requests a second time step_delivered_twice(context, 2) Adds the first 2 requests to the file again: the injected fault.
    When the requests are counted step_count(context) Calls the code under test and keeps its result in context.counts.
    Then zone 161 has 6 trips requested step_check_count(context, 161, 6) Compares the result with the number in the step. A failed assert fails the step.

From the example to your repository

In your repository, the snippets that the dry run prints are the starting point:

  1. Copy the snippets into a Python file in features/steps/.
  2. Add from behave import given, when, then at the top of the file.
  3. Replace each raise line with code. Where two steps differ only in a value, write one function with a parameter.
  4. Run uvx behave@1.3.3 --dry-run --no-snippets. You should see the file and the line of a function after each step that has code, in place of # None.

To run the scenarios of one ID, name its tag: uvx behave@1.3.3 --tags=RF010 (behave: tag expressions).

If your step code imports packages that your project installs with uv, run behave inside the project with uv add --dev behave once and then uv run behave.

Step functions in l19-events

In l19-events, open features/steps/steps.py and features/environment.py. The Given functions read the files that the simulator wrote, the When functions call the code under test, and the Then functions compare the result with the simulator’s known answer.

Level 3 (later, proposed): live cloud runs and an eval as a gate

Live cloud runs behind a tag

The scenarios of Levels 0 to 2 run on your laptop on simulated data. A scenario that calls your deployed system on AWS is slower and spends money, so it runs only when you ask for it. The tag @live marks such a scenario, and a settings file leaves the tag out of a normal run.

  1. Put the live scenarios in a feature file of their own, with @live beside the story’s tag, as shown below. After you save it, check its first line. You should see both @JS01 and @live.

    @JS01 @live
Feature: Trips requested in each zone, on AWS

  @RF010
  Scenario: A request that arrives twice at the deployed pipeline
    Given the counting pipeline is deployed in my AWS account
    When 6 trip requests for zone 161 are written to the stream and 2 of them a second time
    Then the counts table has 6 trips requested for zone 161

  2. Create a file behave.ini at the root of your repository with the two lines below (behave: configuration files). After you save it, run cat behave.ini. You should see the line default_tags = not @live.

    [behave]
default_tags = not @live

  3. Run uvx behave@1.3.3. You should see the live scenario skipped. With this feature beside the Level 1 example, the last lines are:

    1 feature passed, 0 failed, 1 skipped
1 scenario passed, 0 failed, 1 skipped
4 steps passed, 0 failed, 3 skipped
Took 0min 0.001s

  4. When your system is deployed and the live steps have code, run only the live scenarios, at the root of your repository:

    uvx behave@1.3.3 --tags=live

    You should see the steps of the @live scenarios run, and the other scenarios counted as skipped in the last lines.

A live scenario creates data in your account. Remove it in after_scenario, as the teardown at Level 1 does.

In your repository, an ID keeps one rule: a live example can sit under the rule of its ID instead, with @live on the rule, as the rule of RF040 in features/js01_trips_per_zone.feature of the rides example.

Eval as a gate

A part of your system that calls a language model can give a different answer on each run, so a Then with one fixed answer does not test it. An eval runs that part on a set of cases with known answers, each case several times. A gate is a check that fails when fewer runs are correct than the number you chose. The gate is the @eval example under the requirement’s rule, as at Level 0: at this level its steps run the eval, or read a saved eval run, and compare the number of correct runs with the number in its Then.

Live runs and gates in l19-events and recipes

  • Live runs: in l19-events, open behave.ini and features/js01_live.feature.
  • Eval as a gate: in the public recipes, open agent-agentcore/features/eval.feature. In l19-events, open features/js02_eval.feature.
