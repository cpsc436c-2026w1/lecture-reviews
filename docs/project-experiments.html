Experiment examples

Two filled-in examples of experiments/TEMPLATE.md, up to section 6 (Method), which is what the proposal needs. The first compares two ways of storing data on one workload. The second evaluates an assistant over a set of questions with Inspect AI. Both use the same template. They differ in their test cases and in how results are aggregated.

Section 3 follows Kohavi, Tang and Xu, Trustworthy Online Controlled Experiments (2020). It names one overall evaluation criterion (OEC), the metric you compare the alternatives on. It adds guardrail metrics, limits an alternative must stay within to count at all.

Example 1: export format

1. Question. For the nightly export, is Parquet or CSV cheaper to query from Athena when the dashboard reads one day at a time?

2. Design alternatives.

Alternative What it is Why it might win
Parquet the export written as Parquet, partitioned by day Athena reads only the columns and day it needs
CSV the export written as gzipped CSV, partitioned by day simpler to write and inspect

3. Overall evaluation criterion and guardrails.

  • OEC: data scanned per dashboard query (MB), lower is better.
  • Guardrails: median run time per query under 5 s. The rows returned differ in 0 rows between the alternatives.
  • Job story it informs: the dashboard user’s story, for example JS02. Once requirements exist, the requirement written from it.

4. Experiment setup.

  • Same for both alternatives: the same 30 days of data, the same three dashboard queries, the same Athena workgroup.
  • Test cases: one workload, the three dashboard queries over one day.

5. Prediction. Parquet scans about a tenth of the data CSV scans, so it costs about a tenth as much. Run time is similar, because each query reads little data. Source: L7, reading Parquet footers and row groups.

6. Method.

  • Commands: bash experiments/export-format/run.sh parquet, then bash experiments/export-format/run.sh csv.
  • Repeats: 5 runs of each query per alternative.
  • Evidence: evidence/<run id>/ for each run: the command, the commit SHA, Athena’s query statistics, and the script that rebuilds the result table.

Example 2: an assistant evaluated with Inspect AI

A generative-AI-first team on Open Food Facts. The team’s assistant answers questions such as “Which breakfast cereals sold in Canada have under 5 g of sugar per 100 g?” by filling the parameters of one fixed Athena query. Here the test cases are a set of questions with known answers. Each metric is an aggregate over the set.

1. Question. Which of the two course models gives the assistant more correct answers, within our cost and latency limits?

2. Design alternatives. The two models you have access to through the LTIC, served by the model gateway, each behind the same assistant code.

Alternative What it is Why it might win
Qwen 3.6 35B-A3B a mixture-of-experts model: 35B parameters, about 3B active per token fewer active parameters per token, so it may answer faster
Qwen 3.8 27B a dense 27B model, the newer of the two the newer model may follow the tool’s parameters more reliably

3. Overall evaluation criterion and guardrails.

  • OEC: accuracy over all scored answers per alternative (the current questions × 3 epochs), higher is better. A threshold or ranking answer is correct when its product list matches the known list. A count answer is correct when its number equals the known count. An answer to a question the subset cannot answer is correct when it does not return a product list or count and says the product subset does not contain the information needed.
  • Guardrails:
    • accuracy on each question type (threshold, ranking, count, not in the data) at least 70%;
    • F1 of the returned product lists, for threshold and ranking questions, at least 0.8;
    • mean cost under 0.0005 CAD per scored answer, for each alternative over all questions and epochs: (input tokens × input price + output tokens × output price) / 1,000,000, with Inspect’s token counts and the model gateway’s prices in CAD per million tokens from L18 (Qwen 3.6 35B-A3B 0.05 input, 0.10 output; Qwen 3.8 27B 0.10 input, 0.20 output);
    • median latency under 5 s.
  • Job story it informs: the shopper’s question story, for example JS01. Once requirements exist, the requirement written from it.

4. Experiment setup.

  • Same for both alternatives: the same assistant code and system prompt, temperature 0, the same Athena query tool, the same product subset.
  • Test cases: 40 questions, 10 of each type, in experiments/food-qa/questions.jsonl. Each line holds the question, its type and the expected answer: a product list, a count, or “not in the data”. The answers to the first three types are computed once by SQL over the product subset. The fourth type asks about something the subset does not hold, such as a store’s stock today.
  • Cases from failures: when a team member , or another team during testing, reports a wrong answer, check it against the product subset, record its expected answer, and add it to questions.jsonl unless the case is already there. Run both alternatives again on the expanded file before comparing them.

5. Prediction. Qwen 3.8 27B has the higher accuracy, about 85% against 75%. Qwen 3.6 35B-A3B answers faster and stays within the latency guardrail with more room. Token use may differ despite the shared prompt and tool, and Qwen 3.8 27B costs more at equal token counts. Source: L17 for the request path, L18 for the model gateway’s prices.

6. Method.

  • Commands, one per alternative, through the model gateway:
    • inspect eval experiments/food-qa/task.py --model openai-api/proxy/qwen3.6-35b-a3b --epochs 3
    • inspect eval experiments/food-qa/task.py --model openai-api/proxy/qwen3.8-27b --epochs 3
    task.py defines one Inspect task: the dataset is questions.jsonl and the solver is the assistant. The scorer checks product lists for threshold and ranking questions, numbers for count questions, and, for questions the subset cannot answer, that the reply returns no product list or count and says the subset lacks the information. The script that builds the result table from the Inspect logs computes the OEC and its standard error, accuracy by question type, product-list F1, mean CAD per scored answer and median latency, and marks each guardrail as held or not.
  • Repeats: start with 40 questions × 3 epochs, so 120 scored answers per alternative; added failure cases increase both totals.
  • When to run again: after any change to the prompt, the tool or the model, and before the cp2 and final tags. Each run gets its own evidence folder, so the results of different runs can be compared.
  • Evidence: evidence/<run id>/ holds Inspect’s log file for each run, the command, the commit SHA, and the script that rebuilds the result table from the logs.

7. Result, after the run, reports for each alternative: the OEC with a standard error computed across questions (from each question’s mean accuracy over its three epochs), and each guardrail with its value and whether it holds.
