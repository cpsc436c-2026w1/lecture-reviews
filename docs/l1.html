Data larger than memory

Which ways of reading the file stay within 32 GB of memory? *

An online bookshop exports its orders for January 2020 to December 2025 as one CSV file of 24 GB, with 30 columns. An analyst wants the number of orders and the average order value per country for March 2024. The analyst’s laptop has 32 GB of memory, 8 cores and an SSD with 500 GB free. The analyst works in pandas 2, the version before 3.0.

--- shuffle_answers: true --- ## Which of these keep the work within 32 GB of memory while they run? Select every one that does. - [ ] pandas reads the whole file with `read_csv`, then groups by country > An eager load puts the whole file into memory before any grouping. pandas before 3.0 needs about twice the file size in memory because of how pandas stores strings: about 48 GB for the 24 GB file, more than the laptop's 32 GB. The operating system stops the process before the load completes. - [x] pandas reads 1 million rows at a time, adding each to totals > Only one chunk and the running counts and sums per country are in memory at any moment, far below 32 GB. pandas reads all 24 GB, one chunk at a time, and you write the loop yourself. - [x] DuckDB runs the March 2024 query as SQL on the CSV file > One chunk per core and the running counts and sums per country are in memory at any moment, far below 32 GB. DuckDB reads all 24 GB, one chunk at a time on each core, and organizes the loop for you. - [ ] pandas reads the whole file with `read_csv` from a faster SSD > An eager load puts the whole file into memory before any grouping: about 48 GB for the 24 GB file with pandas before 3.0. A faster SSD reads the file sooner, but the load still needs about 48 GB of memory, so the operating system stops the process before the load completes. - [ ] pandas reads the whole file on an m6a.2xlarge (8 vCPU, 32 GiB) > An eager load puts the whole file into memory before any grouping: about 48 GB for the 24 GB file with pandas before 3.0. The instance has 32 GiB, about what the laptop has, so the operating system stops the process there too.

Parquet on S3: reading only what you need

May 2025 downloads: reading the file over the network

A podcast platform keeps its episode downloads for January 2024 to December 2025 as one Parquet file in S3:

downloads.parquet    4.8 GB, 40 columns, each column about 120 MB of the file
                     rows sorted by download time
                     24 row groups of about equal size, one per month, 200 MB each

A query counts downloads per episode for May 2025 and uses 6 of the 40 columns. The footer at the end of the file holds each row group’s min and max download time.

--- shuffle_answers: true --- ## DuckDB on a laptop reads downloads.parquet directly from S3 using `httpfs`, its extension for reading remote files. About how many MB does it fetch for the May 2025 query, not counting the footer? 1. [x] 30 MB > The footer's min and max show that only 1 of the 24 row groups holds May 2025, and from it DuckDB fetches only the 6 columns' chunks: 6 × 120 MB / 24 = 30 MB. DuckDB reads the footer first and works out which byte ranges hold those chunks. S3 returns only the byte ranges DuckDB asks for, and S3 itself does not choose columns or rows. 1. [ ] 720 MB > 720 MB is the 6 columns from all 24 row groups. The rows are sorted by download time, so the footer's min and max rule out the 23 row groups that hold no May 2025 downloads. 1. [ ] 200 MB > 200 MB is every column of the May row group, as if a row group had to be read in full. Each column has its own chunk inside the row group, so DuckDB does not fetch the other 34 columns. 1. [ ] 4,800 MB > Fetching 4,800 MB means reading every row group and every column. The rows are sorted by download time, so the footer's min and max rule out the 23 row groups that hold no May 2025 downloads. Each column has its own chunk, so DuckDB does not fetch the other 34 columns.

The platform then rewrites the same downloads into a new file of the same size, with the rows not ordered by time: each of the 24 row groups now holds downloads from all 24 months. The columns, their sizes and the query stay the same.

--- shuffle_answers: true --- ## About how many MB does DuckDB fetch from the rewritten file for the May 2025 query, not counting the footer? 1. [x] 720 MB > Every row group's min and max now span all 24 months, so none can be ruled out. DuckDB still fetches only the 6 columns' chunks: 6 × 120 MB = 720 MB. 1. [ ] 30 MB > Choosing 30 MB assumes that one row group holds all of May 2025, as in the sorted file. In the rewritten file every row group's min and max span all 24 months, so none can be ruled out and DuckDB fetches the 6 columns' chunks from all 24 row groups. 1. [ ] 200 MB > Choosing 200 MB assumes that one row group still holds all of May and must be read in full. In the rewritten file every row group's min and max span all 24 months, so none can be ruled out, and DuckDB fetches only the 6 columns' chunks, from all 24 row groups. 1. [ ] 4,800 MB > Every row group must now be read, and each column still has its own chunk in every row group, so DuckDB fetches only the 6 columns' chunks and not the whole file.

Pattern of use

Which resource is the bottleneck of each job? *

Each job below runs on a laptop with this setup:

memory     16 GB
compute    8 cores and a GPU
storage    an SSD with 500 GB free, which reads and writes about 2 GB/s
network    a home connection of 100 Mbps, about 12 MB/s
--- shuffle_answers: true --- ## Which resource is the bottleneck of each job? Each option may be used once, more than once, or not at all. - Gradient boosting with 2,000 trees on a 4 GB table in memory; one core is at 100% for 5 hours :: compute > The trees are built one after another, because each tree depends on the last. The work inside each tree can be split across cores; this run uses one core, which stays at 100% the whole time. The 4 GB table fits in memory, and storage and network do not limit the job, so that core is the bottleneck. - Turning 500 hours of recorded interviews into text with a speech model on the laptop's GPU, which stays at 100% for the whole run :: compute > The GPU stays at 100% the whole time. The SSD reads the recordings much faster than the model processes them, so the GPU is the bottleneck. - A dashboard downloads a whole 6 GB Parquet file from S3 on every refresh, and each refresh takes about 8 minutes :: network > At 12 MB/s, transferring 6 GB takes about 8 minutes, so the network connection is the bottleneck. Reading only the needed columns and row groups would reduce the amount of data transferred over the network. - Copying 350 GB of satellite images from S3 to the SSD; the copy takes about 8 hours :: network > At 12 MB/s, transferring 350 GB takes about 8 hours, so the network connection is the bottleneck. The SSD has enough space and can write much faster than the network can deliver data. - A pandas pivot turns a 5 GB sales table into a wide table of about 22 GB; the SSD stays busy as the operating system moves data from memory to the SSD, and then the operating system stops the process running the pivot :: memory > The wide table alone is larger than the 16 GB of memory, so the operating system stops the process before the pivot completes. - Fitting a model that must hold every row of its 24 GB feature table at once :: memory > Every row is needed at the same time, so there is nothing to skip: 24 GB does not fit in 16 GB of memory. - :: storage > The SSD has space for every file here and reads about 2 GB/s, faster than any of these jobs needs. In the pivot, the SSD is busy only because memory is full and the operating system moves data from memory to the SSD; memory is the bottleneck.

Cost granularity

How does the cost of one weekly run compare? *

A pharmacy chain runs a weekly report over 40 GB of prescription records. Both instances below are in ca-central-1 and are billed per second, and each instance is terminated when the report is written:

m6a.xlarge     4 vCPU, 16 GiB    $0.1926 an hour
               6 hours: the data does not fit in memory,
               so it is read from disk on every pass
m6a.4xlarge   16 vCPU, 64 GiB    $0.7704 an hour
               1 hour: the data fits in memory
--- shuffle_answers: true --- ## How does the cost of one run on the m6a.4xlarge compare with one run on the m6a.xlarge? 1. [x] Less per run on the m6a.4xlarge > 1 hour × \$0.7704 is about \$0.77 a run, against 6 hours × \$0.1926, about \$1.16. You pay for the time you use, so the instance that costs four times as much per hour is cheaper per run when the report finishes six times sooner. 1. [ ] More per run on the m6a.4xlarge > The m6a.4xlarge costs more per hour, \$0.7704 against \$0.1926, and the hourly price is not the price of a run. Billed per second, a run costs the hourly price times its hours: about \$0.77 against about \$1.16. 1. [ ] Same per run on both > The cost would be the same if four times the vCPUs made the job exactly four times faster, 1.5 hours. The data also fits in the m6a.4xlarge's 64 GiB, so the job runs six times faster.

Who is responsible for what

Your research team stores its survey responses in a managed database service on AWS, a platform as a service (PaaS): you create tables, load the data and write SQL queries, and pay for the service by the hour.

Terms used on this page

From the course flashcards, grouped by topic. Practise them in quiz mode, or try the match game.

Memory and resources

Storage, memory, compute and network. The four things every data task uses, each with a capacity and a rate. Looking at a job from each in turn helps find its bottleneck, and cloud architecture often trades one for another.

Eager load. Reading the whole dataset into memory before the work starts. If data and working space exceed memory, the operating system swaps to disk or stops the program.

Parquet

Parquet. A columnar file format. Rows are grouped into blocks that each store every column separately, and metadata at the end of the file says where each part is.

Row group. A horizontal block inside one Parquet file, holding one column chunk per column. Its size is set when the file is written, and a file can hold one or many.

Column chunk. The values of one field within one row group of a Parquet file. The writer can store their min and max, which lets a reader skip the whole row group.

Footer. The metadata at the end of a Parquet file: the schema, where each column chunk starts and, if the writer stored them, each chunk’s min and max. A reader fetches it before any data.

Projection pushdown. Handing the reader the list of columns a query uses, so it reads only those columns from a Parquet file.

Predicate pushdown. Handing the reader the query’s filter, so it can skip row groups whose stored min and max show that no row can match.

Files on S3

S3. AWS’s object store. You reach each object over the network by its name inside a bucket, and the data stays with no server running.

Byte-range read. Asking S3 for one stated part of an object instead of the whole object. Parquet libraries fetch the footer this way, then only the column chunks a query needs.

Also used on this page

Instance (EC2). A virtual machine you rent from AWS, billed per second for the time it runs. Stopping it ends the compute charge, but its EBS disk still bills.

Instance type. The size you pick when you launch an EC2 server: how many vCPUs and how much memory it has, how fast its network is, and whether it has its own local disk.

Cost granularity. The unit a provider bills in, such as one second of instance time or one request. With per-second billing, a faster, pricier instance can come out cheaper per task.
