Which fix handles which situation

Which lakehouse feature handles each situation in an online shop’s orders table?

An online shop keeps its orders in an Iceberg table in the Glue Data Catalog, over Parquet files in S3. Each order has an order_time, and the table is partitioned by the day of order_time. A load adds new orders every hour, and corrections change rows. Athena reads and changes the table.

--- shuffle_answers: true --- ## Match each situation to the lakehouse feature that handles it. Not all options will be used. - An auditor asks what yesterday's total sales were before this morning's correction, while that snapshot is still retained :: Time travel > Each data change creates a snapshot that is kept until it is expired, and a query can read the snapshot that was current before the correction (P5). - After weeks of hourly loads the table holds thousands of small files, and every query starts slowly :: Compaction > Compaction rewrites many small data files into fewer larger ones (P3). The manifests already save the folder listing; the small files are what remains to fix. - A dashboard query runs while a load is adding new orders; it must show all of that load or none of it :: Table commit > The load becomes visible in one step, when the catalog entry switches to the new metadata file (P1). - Test orders must disappear from the table, and the data files that hold them must not be changed :: Delete files > A delete file is a small file that lists which rows of a data file are deleted; readers skip those rows, and the data file itself is not changed. Athena's `DELETE` writes one (P4, no change or delete in place). The `DELETE` is also a commit, but the commit alone does not say how rows are removed. - A query filters on `order_time` for one afternoon and opens only that day's data files, without naming any folder :: Iceberg partitioning > The table is partitioned by the day of `order_time`, a value Iceberg derives from the column (hidden partitioning), so a filter on the column itself skips other days' files (P2). - :: `_SUCCESS` file > Spark writes it at the end of a job, but readers of a folder do not check it by default, so it does not make a write all-or-nothing. - :: Folder partition column > The data lake's workaround for P2: it skips day folders only when the query's filter uses the folder partition column.

Choosing an engine for a regular workload

Five steps, from naming the inputs to your own cost comparison (a crossover). Steps 1 and 2 are quizzes; step 3 is a worked example to read; in step 4 you finish one; step 5 you do alone. A3 task 2 asks for the same on the branch’s loads. We’ve seen this cost recipe on the D3 redesign slide (steps 3-5).

Step 1: where do you get each piece of information?

A team runs the same report queries on Athena every day and asks whether to move them to Trino on an EMR cluster.

## Where do you get each piece of information for this decision? Each option may be used once, more than once, or not at all. - Data scanned by each report query :: Athena query history > Athena records each query's Data scanned. For billing, AWS rounds it up to the next MB, with a 10 MB minimum per query; the billed amount per run × price per TB × runs a day is Athena's daily cost, as in step 3. - Expected report load next year: runs per day and the most runs in one hour :: Stakeholders and business case > The people who use the report know how often they will run it. Runs per day multiply Athena's daily cost, and the busiest hour decides how much cluster capacity is needed. How often it ran in the past is in Athena query history. - Run time of one report on a cluster :: Pilot run on a cluster > Run time on the cluster you are considering tells you how many reports its nodes can serve in the hours it is up. - Cluster's resource ceiling for your report (the most runs an hour it can keep up with) :: Pilot run on a cluster > Running reports in parallel on the pilot cluster shows how many runs an hour its nodes can finish; compare that ceiling with the busiest hour's load. - Price per TB of Data scanned :: AWS price list > With Data scanned per run and runs a day, it gives Athena's daily cost, for your Region. - Price per hour of each node :: AWS price list > EC2 price plus EMR price for the node type, times the number of nodes and the hours they are up, gives the cluster's daily cost; each node is billed per second while it is up, with a one-minute minimum. - Budget for running the reports :: Stakeholders and business case > The crossover says which option is cheaper; the budget says whether that option is affordable. - How soon after a request an answer is needed :: Stakeholders and business case > A cluster started on demand makes the first report wait while it starts; a cluster kept up for quick answers is billed while it waits. - Who would look after a cluster :: Stakeholders and business case > Auto-termination, software updates and failed nodes need someone's time, which belongs in the decision even though it is not on the bill. - :: S3 storage bill > The tables stay in S3 whichever engine reads them, so storage is the same in both options and does not decide between them.

Your pilot measured one report query: about 3 GB of Data scanned on Athena, about 10 seconds on a 3-node EMR cluster, and about 2 minutes as a Glue job (Glue version 5). Here “EMR cluster” means everything its nodes are billed for: the EC2 price and the EMR price.

Step 3, read: worked example, Athena or a cluster?

A report query runs on Athena today. Would 3 nodes running Trino on EMR be cheaper?

Input Value Where you read it
Expected load 500 runs a day, at most 60 in the busiest hour stakeholders and business case
Run time on 3 nodes 10 s per run Trino web UI, Elapsed, from a pilot run
Data scanned per run 3 GB = 0.003 TB Athena query history, or Data scanned under the results in the editor
Athena price $5.50 per TB of Data scanned AWS Athena pricing page, Canada (Central)
Cluster up 10 hours a day stakeholders and business case
Node price $0.22 per node-hour EC2 m7g.xlarge $0.18 + EMR $0.04 per hour, AWS pricing pages
  1. Fit first. Busiest hour: 60 runs × 10 s = 600 s of work. Running one report at a time, the 3 nodes’ ceiling (the most work they can keep up with) is 3,600 s of work an hour, so the load fits. (If it did not, you would size the cluster up and price the bigger one.)
  2. Athena, a day. 0.003 TB × $5.50 per TB = $0.0165 a run; 500 runs × $0.0165 = $8.25.
  3. Cluster, a day. 3 nodes × $0.22 per node-hour × 10 hours = $6.60 for any load under its ceiling.
  4. Crossover. $6.60 ÷ $0.0165 = 400 runs a day. At 500 a day the cluster is cheaper; below 400, Athena is.

Not counted: the minutes a cluster takes to start (its nodes are billed then too) and S3 requests.

Step 4, finish it: Glue or the same cluster?

The same report could run as a Glue job instead. Compare it with the same cluster as in step 3: 3 nodes, up 10 hours a day, $6.60 a day.

Input Value Where you read it
Expected load 500 runs a day as in step 3
Workers 2 DPU (2 G.1X workers) Glue job run details, Worker type and Number of workers (G.1X = 1 DPU each)
Billed time per run 2 minutes Glue job run details, Execution time; at least 1 minute is billed
Glue price $0.44 per DPU-hour AWS Glue pricing page, Canada (Central)
Cluster, a day 3 nodes × $0.22 × 10 hours = $6.60 step 3

Fill in the blanks on paper, then open the answer.

  1. Glue, one run: 2 DPU × 2 minutes = ___ DPU-minutes = ___ DPU-hour; × $0.44 = ___ a run.
  2. Glue, a day: 500 runs × ___ = ___, against the cluster’s $6.60.
  3. Crossover: $6.60 ÷ ___ ≈ ___ runs a day. Which is cheaper above the crossover, and which below it? Which fits occasional runs?
TipAnswer, step 4
  1. 2 × 2 = 4 DPU-minutes = 4/60 DPU-hour; 4/60 × $0.44 ≈ $0.02933 a run.
  2. 500 × $0.02933 ≈ $14.67 a day, against $6.60.
  3. $6.60 ÷ $0.02933 ≈ 225 runs a day. Above about 225 runs a day the cluster is cheaper (at 500 a day, $6.60 against $14.67); below it, Glue is. For occasional runs Glue is cheaper: each run bills about 3 cents, while the cluster’s nodes are billed for their 10 hours a day.

No fit check here: each Glue run gets its own workers. Glue bills each run’s execution time, at least 1 minute.

Step 5, on your own: new workload

An online shop’s sales report:

Input Value
Expected load 120 runs a day, at most 20 in the busiest hour
Data scanned per run on Athena 5 GB
Run time on 3 nodes 15 s per run
Cluster up 12 hours a day, at $0.22 per node-hour
As a Glue job 2 DPU, 1.5 minutes billed per run, $0.44 per DPU-hour
Athena price $5.50 per TB of Data scanned

Work through the same four steps as in step 3, then price Glue as in step 4. Which of the three is cheapest at 120 runs a day?

TipAnswer, step 5
  1. Fit: 20 × 15 s = 300 s of work in the busiest hour, under the 3 nodes’ ceiling of 3,600 s.
  2. Athena: 0.005 TB × $5.50 = $0.0275 a run; 120 × $0.0275 = $3.30 a day.
  3. Cluster: 3 × $0.22 × 12 = $7.92 a day.
  4. Crossover, Athena against the cluster: $7.92 ÷ $0.0275 = 288 runs a day; at 120, Athena is cheaper.
  5. Glue: 2 × 1.5 = 3 DPU-minutes = 0.05 DPU-hour × $0.44 = $0.022 a run; 120 × $0.022 = $2.64 a day.

Glue is cheapest here: each run scans 5 GB, which Athena bills by the TB, while Glue bills 1.5 minutes. Use rules of thumb only as an initial guide; use the cost calculation for the final choice. Glue’s runs also wait while workers start, which matters if someone waits for the report.

Terms used on this page

D1 catalog and table format

CTAS (CREATE TABLE ... AS SELECT). Writes a query’s result as a new table.

UNLOAD. Runs a query and writes its result as files to an empty S3 location, with no table.

ALTER TABLE ... ADD COLUMNS. A schema change, written as a new metadata file with no new snapshot.

Metadata tables ("t$partitions", "t$files", "t$snapshots", "t$history"). Read-only tables Athena makes from an Iceberg table’s metadata, one row per partition, data file or snapshot.

Snapshot operation. What $snapshots records for each snapshot: append (files added), overwrite (rows deleted or changed), replace (files rewritten, rows unchanged).

Field id. The number Iceberg gives a column when it is added. column_sizes in $files is keyed by it.

D2 layout

Partition spec. A source column and a transform, such as months(pickup_datetime); Iceberg derives each file’s partition value from it.

Sort order (WRITE ORDERED BY). The order Iceberg asks writers to sort rows in within each file, so each row group covers a narrow range.

Row-group size (write.parquet.row-group-size-bytes). The size at which the Parquet writer starts a new row group.

Projection pushdown. The engine hands the reader the query’s columns, so the others are never read.

D3 query engine

DPU-seconds. What a Glue run is billed for, DPUs × seconds of run time with a 1-minute minimum, at the DPU-hour price.

Data scanned limit. A per-query limit on an Athena workgroup. A query that passes it is cancelled and billed for the Data scanned before it stopped.

D4 corrections

Delete file. A file that lists rows removed from a data file. Readers skip those rows, and the data file stays as written.

MERGE. One statement that updates the rows whose key matches a source row and inserts the rest.

D5 upkeep

OPTIMIZE ... REWRITE DATA USING BIN_PACK. Compaction in Athena: rewrites small files into larger ones, recorded as a replace snapshot.

VACUUM. Expires snapshots older than the table’s age property, then deletes the files no remaining snapshot lists. Expired snapshots cannot be read.

Table property. A setting kept in the table’s metadata file, such as vacuum_max_snapshot_age_seconds.

D6 object storage

Storage class. S3’s price tier for an object: lower monthly price, a fee per GB read and a minimum duration.

Lifecycle rule. An S3 bucket rule that moves or deletes the objects under a prefix a set number of days after they were written.

Lake and lakehouse

Data lake. Raw files in object storage, read by engines that list the folders; a folder of files has no commit, no record of its schema and no history.

Lakehouse. A lake whose tables have a table format and a catalog, so readers see whole commits.

Query engine. Parses SQL, plans it and runs it: Spark SQL, Trino, DuckDB, Athena.

Catalog. Lists tables and points to each table’s current metadata file: the Glue Data Catalog.

Table format. Metadata files that say which data files are the table now, with the schema and the snapshots: Iceberg.

Object storage. Keeps files as objects in buckets: S3. Which files form a table is recorded in the metadata above it.

Storage format (file format). Encodes rows in one data file, with a footer: Parquet.

Iceberg’s levels

Catalog entry. The table’s name and the path of its current metadata file.

Metadata file. The schema, the partition spec (how files are grouped, for example by month) and the snapshots; each snapshot names a manifest list.

Manifest. Lists data files, each with its partition value, row count, and minimum and maximum per column.

Data file. A file that contains rows of a table: a Parquet file.

Commit. Writing new metadata files, then switching the catalog entry to the new one in one step; readers see the old snapshot or the new one, never half.

Snapshot. One version of the table: the data files that were the table after one commit.

What the table format fixes

Iceberg partitioning. The table is partitioned by a value Iceberg derives from a column, for example the month of pickup_datetime, and each data file’s partition value is kept in the manifests. Because the value is derived (hidden partitioning), a filter on the column itself skips files, with no folder partition column to name. Separately, the manifests keep each file’s minimum and maximum per column, which also let an engine skip files.

Delete file. A small file that lists which rows of a data file are deleted. Readers skip those rows, and the data file itself is not changed.

Compaction. Rewriting many small data files into fewer larger ones (OPTIMIZE).

Time travel. Reading the table as it was at an earlier snapshot, as long as that snapshot has not been expired.

Not layers of a lakehouse

Cluster manager. Starts an engine’s processes on a cluster’s nodes, for example YARN starting Spark’s executors on EMR (L5).

Connector. In Trino, how the engine reads one source, such as the Glue Data Catalog or a database (L10).

_SUCCESS file. An empty file Spark writes when a job finishes writing a folder; readers of the folder do not check it by default.

Folder partition column. A column whose value is a folder name, such as month=2024-03; a data lake skips folders only when a query names it.
