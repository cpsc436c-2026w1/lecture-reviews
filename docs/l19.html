L19 review: from Feedback 1 to Checkpoint 1

If you need to look up a term, the relevant vocabulary is below. The first part recaps L18; the second reviews the L19 studio, which took one requirement from your Feedback 1 issue to a dry run for Checkpoint 1.

Recap of L18

What decides the steps at the pet-food shop?

--- shuffle_answers: true --- ## A pet-food shop runs a chat that can search its products and read the signed-in customer's orders. A nightly job loads the supplier's price file into the product table, and an alarm fires when the load goes wrong. For each piece of work, choose what decides its steps. Each option may be used once, more than once, or not at all. - A customer asks “where is my last order?”, and for every question of this kind the chat reads the signed-in customer's newest order and shows its status :: App code > The steps are known before any request arrives: one look-up, then the reply. Code runs them every time, and no model call chooses them. A planner call or an agent would spend model calls on steps that never change. - The nightly load fails because the price file arrived after the load had started, a cause that the team's runbook checks by comparing the file's arrival time with the load's start time :: App code > A runbook in code checks the causes seen before against the data, without a model call. A late file is one of them, so the data settles the alarm. An agent runs only when the runbook's checks do not settle the alarm. - A customer asks for “food for a new puppy and an older cat”. The shop has no fixed rules that turn a request like this into searches, and the search results go into the reply, not into choosing more searches :: Planner model call > The kinds of food depend on the request, so one model call lists them before anything runs. App code caps the list and runs one search for each kind. An agent is not needed, because no search result changes which kinds are searched. - A customer asks for “what a kitten needs in its first week”. The shop's code does not list the supplies for a request like this, and the search results are used to choose products, not further searches :: Planner model call > The shop has no fixed rules that list the supplies for every request written in free text, so a model call returns the list. Every part is known before the searches run, so app code can check the list and then run it. - The nightly load fails, the checks for the causes seen before find none of them, and which log or file to read next depends on what the last read showed :: Bounded agent > The model chooses each next read-only tool call from the results so far, within limits that it cannot remove. A list of steps written before the first read could not follow the evidence. App code then checks the cause that the agent names. - After a failed load, the runbook names a missing file, but the file is there and has its usual rows. The runbook does not have a check for this, and which table or log to read next depends on what each read shows :: Bounded agent > The data does not confirm the runbook's answer, so the alarm is not settled. The model chooses each next read from what the earlier reads returned, and app code checks the cause it names against the data. - :: Model gateway > Every row asks what decides which steps run. The model gateway sits on the way to the model and checks the key, the request rate and the budget of a call that is already being made, so it does not choose the steps in any of these rows.
Term What it means
Orchestrator-workers A planner model call splits the request into subtasks that depend on it. App code bounds the plan, runs a worker for each subtask and combines the results.
Plan, validate, then execute App code checks a plan before it runs: a cap on its steps, known tables and columns only, and Data scanned under a cap.
Agent loop The model returns a tool call, app code runs it and sends the tool result back, and the model returns the next tool call or the final reply.
Bounded agent An agent with limits on its actions, time or spend that the model cannot remove. Reaching a limit stops the loop.
Runbook first App code checks the causes seen before, with no model call. The agent runs only when the data does not settle the alarm, and app code checks the cause it names.

Use a planner when the steps cannot be fixed in advance. Use code when the steps are known.

Read more: AI Engineering, ch. 6, “Planning”, “Agent Overview”.

Review questions for L19

The questions follow a library team through its Checkpoint 1 hand-in. The team’s project counts the books returned at each drop box of a city library. Each drop box sends one event for each returned book.

Each option may be used once, more than once, or not at all. - RF010: every returned book is counted once, even when a drop box sends its event twice :: Rule with an example > A test can check this constraint: a book whose event arrives twice either changes the count or does not. Its line under `Stakeholder input` ends with `[Scenario](…)`, and its rule in the feature file carries the tag `@RF010`. - RF020: a drop box that sends no event for 30 minutes is shown as silent, not as 0 returns :: Rule with an example > A test can check this constraint. An example leaves out every event of one drop box for 30 minutes, and its `Then` checks that the dashboard shows that box as silent. - RF050: every AWS resource of the team carries the course tags :: Line only, no rule > Staff check the tags by reading the scripts and the tags on the resources, not by running an example. The line under `Stakeholder input` ends with `Read at Checkpoint 2:` and names what staff will read. - RQ020: say how long raw drop-box events are kept and who may delete them :: Line only, no rule > A request is answered in writing, so it does not get a rule. Its line under `Stakeholder input` then says where: `Done in docs/proposal.md, section 3.` - RQ030: Fix: the sketch in section 5 leaves out the stream between the drop boxes and the counting function :: Correction in `docs/proposal.md` > The team draws the missing stream in the proposal's sketch, and the line under `Stakeholder input` says `Done in docs/proposal.md, section 5.` A request that starts with `Fix:` does not wait for Checkpoint 2. - :: Step code > Step code, the Python functions that make the steps run, is Checkpoint 2 work. At Checkpoint 1 `features/steps/` holds only `.gitkeep`. - :: Answer in `docs/design.md` > The answer to a request that does not start with `Fix:` is due at Checkpoint 2. At Checkpoint 1 the request's line has a `Reply:` that says what the team will do.

Which EARS form fits each requirement of the drop-box counter?

The team writes the requirements of its job stories in EARS. Readers use the library’s app.

--- shuffle_answers: true --- ## For each requirement of the drop-box counter, choose the EARS form it should be written in. Each option may be used once, more than once, or not at all. - A 10-minute period ends, and the system stores one count of returned books for each drop box in that period :: `WHEN <trigger>` line > The end of a period is an event that starts the response, so the line starts with `WHEN`. Nothing has gone wrong, so the line does not start with `IF`. - A reader enters a library number at a drop box, and within 2 seconds the box's screen shows the reader's books on loan :: `WHEN <trigger>` line > Entering the number is an event that starts the response, and the 2 seconds go after `|` as the performance target. Nothing has gone wrong, so the line does not start with `IF`. - For as long as a drop box is marked full, the app shows readers the nearest drop box with space :: `WHILE <state>` line > Being full is a state that lasts until the box is emptied, and the app shows the other box for the whole time. A `WHEN` line would answer one moment, not the time in between. - For as long as a book is on loan past its due date, the app shows the reader the late fee so far :: `WHILE <state>` line > An overdue loan is a state that lasts, and the response holds while the state holds. A late loan is the reader's state, not a problem in the team's data, so the line does not start with `IF`. - A drop box sends the event of one returned book twice, and the system counts that book once :: `IF <problem> THEN` line > A repeated event is a problem in the data that would make the outcome false: the count would be one too high. A problem gets an `IF … THEN` line. - A drop box stops sending events for 30 minutes, and the dashboard shows that box as silent, not as 0 returns :: `IF <problem> THEN` line > Input that stops is a problem that would make the outcome false, because a broken box and an empty box would both show 0. Interrupted input is trouble, so it gets an `IF … THEN` line; `WHILE` is for a normal state, such as a full box. - :: `WHERE <feature>` line > A `WHERE` line is for behaviour that exists only when an optional feature is part of the system, such as an assistant. A requirement that holds without any optional feature does not start with `WHERE`.

How does behave count each step?

The team runs behave on its feature files. behave’s last line counts the steps, such as 47 steps passed, 3 failed, 0 skipped, 44 undefined.

--- shuffle_answers: true --- ## For each step, choose the word that behave's steps line counts it under. Each option may be used once, more than once, or not at all. - In a normal run, a `Then` step's function runs, and its `assert` compares the expected 2 returned books with the 3 that the system counted :: Failed > The function ran and its `assert` did not hold, so the step fails, and behave prints the assert's message with both numbers. - In a normal run, a `Then` step's function runs, and its `assert` expects drop box B7 to show as silent, but the system shows B7 with 0 returns :: Failed > behave ran the step function, and the `assert` inside it did not hold, so the step is counted as failed. The step has a function, so it is not undefined. - In a dry run of the Checkpoint 1 draft, a `Given` step that has no step function, because `features/steps/` holds only `.gitkeep` :: Undefined > No step function matches the step's text, so the step is undefined, and behave prints a snippet for it. A dry run does not run any step, so it does not report a step as passed. - In a normal run, a `When` step whose text matches no step function, because the team wrote new wording :: Undefined > behave finds a step function by the step's text. New wording needs new step code, so the step is undefined. - In `uv run behave --tags=@R030`, a step of a scenario that only the tag `@R040` covers :: Skipped > `--tags=@R030` runs only the scenarios under that tag, so behave does not run this step and reports it as skipped. - In `uv run behave --tags=@RF020`, a `Given` step of an example under the rule tagged `@RF010` :: Skipped > The run includes only the scenarios under `@RF020`. The example under `@RF010` is left out, so behave does not run its steps. - :: Error > `error` is a word of the scenarios line, not of the steps line. behave counts a scenario as an error when one of its steps is undefined, and it counts that step as undefined.

What does the example report with the duplicate check off?

One example of the team’s rule for RF010:

Example: One return delivered twice
  Given only these return events are received:
    | event_id  | drop_box | event_time | received_time |
    | ev-000201 | B12      | 10:11:00   | 10:11:01      |
    | ev-000202 | B12      | 10:12:30   | 10:12:31      |
    | ev-000201 | B12      | 10:11:00   | 10:12:40      |
  When the counts are read at 10:15:30
  Then drop box B12 shows 2 returned books between 10:10 and 10:15

The third row repeats the first row’s event_id: the same return delivered twice. For one run, the team turns the counting function’s duplicate check off; the test stays the same.

[x] Fails: expected 2, counted 3 > Without the duplicate check, the return delivered twice is counted twice, so the system counts 3. The `Then` compares that count with the 2 worked out from the rows before the run, so the failure message shows both numbers. 1. Terms used on this page

Recap of L18

Orchestrator-workers. A planner model call splits the request into subtasks that depend on it. App code bounds the plan, runs a worker for each subtask and combines the results.

Agent loop. The model returns a tool call, app code runs it and sends the tool result back, and the model returns the next tool call or the final reply.

Bounded agent. An agent with limits on its actions, time or spend that the model cannot remove. Reaching a limit stops the loop.

Runbook first. App code checks the causes seen before, with no model call. The agent runs only when the data does not settle the alarm, and app code checks the cause it names.

Model gateway (L16). A service between apps and model providers. It can hold the provider key, check each key’s budget and forward the calls.

Feedback IDs and requirements

Feedback 1 issue. The GitHub issue staff-feedback in your repository, where staff listed constraints (RF) and requests (RQ) about your proposal.

Constraint (RF010 …). A property of your system from your Feedback 1 issue. One that a test can check gets a rule; one that no test can check ends with Read at Checkpoint 2: … and what staff will read.

Request (RQ010 …). Something staff ask your team to do or answer. A request that starts with Fix: is corrected in docs/proposal.md; any other request gets a Reply: that says what you will do, and its answer is due at Checkpoint 2.

Stakeholder input. The section of docs/requirements.md with one line for each RF and RQ ID of your Feedback 1 issue, with its wording and your Reply:.

Job story. Each job story from your proposal that you plan to implement, as a heading with its ID (JS01 …) in docs/requirements.md.

EARS (Easy Approach to Requirements Syntax). One sentence of the same shape for every requirement: a keyword says when it applies, and THE SYSTEM SHALL says what the system then does. No keyword: always; WHEN <trigger>; WHILE <state>; IF <problem> THEN; WHERE <feature>.

Traceability. Each ID is defined once in docs/, and every other place that uses it names it: a tag in features/, a cell in docs/design.md.

Data and examples

Event. A record that says something happened.

Delivery. One arrival of an event at the system. received_time is when it arrived; event_time is when it happened.

Event format. One line for each kind of event in docs/design.md, section Data, naming the fields that your examples’ tables use.

Injected fault. A problem added to the test data on purpose, with an exact count, and recorded so the test knows the right answer. The system is not told which events are faulty.

Simulated data set (SIM01 …). A named set of generated test events or rows, for an example that needs more events than a small table holds. At Checkpoint 1 it is one bullet of words in docs/design.md, section Data.

Example. Test data and an expected answer: Given the data, When something happens, Then an answer known before the system runs.

Eval in words. An entry under Evals in docs/requirements.md for a requirement on a model’s answers: the cases, what counts as correct, the runs, when it passes, and the model in use.

Feature files and behave

Gherkin. The plain-text format that uses Feature, Rule, Example, Given, When and Then.

behave. A Python tool that reads Gherkin feature files and runs them.

Feature file. Plain text in features/, named for what the user gets.

Rule. A group of scenarios that show one requirement, with the requirement’s ID as its tag.

Tag. A label such as @R020 on the line above a feature, a rule or a scenario. It applies to everything under it.

Step function. Python code in features/steps/ that behave calls for a step with matching text.

Background. Steps that run before every scenario of the feature.

Scenario Outline. Steps with <placeholders>, run once for each row of its Examples: table.

Dry run. behave reads the feature files and matches each step with step code, without running it.

Undefined step. A step without step code. behave prints a snippet for it: the empty step function to write later.

Pull request. A proposed change for review. The Checkpoint 1 hand-in is a merged pull request with the tag cp1 on the merged commit.
