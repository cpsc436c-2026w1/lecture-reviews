L6 review: how Spark runs a query, and why it might be slow

The scenarios follow the lecture’s worked example and its measured runs, except the spill scenario in the last part, whose numbers are made up for practice. If you need to look up a term, the relevant vocabulary is below.

* Not asked on the midterm; good practice for the course.

How Spark runs our query

Where does each step of the query run?

The lecture’s example data are the New York City yellow taxi trips from 2011 to 2013, about 520 million trips in 36 monthly Parquet files on S3. An EMR cluster of 1 primary and 2 core nodes, all m7g.xlarge, runs the query from L5: the rides and the average total per payment type for June 2012. Each core node has one executor with 4 cores, so the cluster has 8 slots.

by_pay = (spark.read.parquet("s3://…/taxi/parquet/")
  .filter((F.col("tpep_pickup_datetime") >= "2012-06-01")
        & (F.col("tpep_pickup_datetime") <  "2012-07-01"))
  .groupBy("payment_type")
  .agg(F.count("*").alias("rides"),
       F.avg("total_amount").alias("avg_total")))
by_pay.collect()
--- shuffle_answers: true --- ## For each step of the June 2012 query, where does it run? Each option may be used once, more than once, or not at all. - read the trip rows from the files: `spark.read.parquet` / `FROM` :: task, on its own Spark partition > Each task reads its own Spark partition, without rows from any other Spark partition. The Spark partition is a set of byte ranges of the files. The task reads every row of each row group whose middle falls in one of its ranges, and only the needed columns. A task whose ranges hold no row group's middle reads no rows: 16 of the 52 tasks here. - keep only the trips for June 2012: `filter` / `WHERE` :: task, on its own Spark partition > Each task filters its own Spark partition, without rows from any other Spark partition: it keeps or drops each row it holds. - drop the columns no longer needed (Spark adds this step itself) :: task, on its own Spark partition > Each task drops the columns on its own Spark partition, without rows from any other Spark partition: it keeps only `payment_type` and `total_amount` on the rows it already holds. Reading only the needed columns happened earlier, in the scan. - finish the count and average per payment type: `groupBy().agg()` / `GROUP BY` :: task, after the `Exchange` > A task can total its own rows, but Spark plans the step before it knows where the rows are, and a payment type's rows can be in any Spark partition. So the partial totals go into an `Exchange` first, even in the measured run, where one task held every June 2012 trip. "Driver" is wrong here: the driver never adds up trip rows. - return the answer to your program: `collect()` :: driver > `collect()` returns the 5 final rows to the driver, the process that runs your program. - :: YARN, on the primary node > Picking YARN confuses the cluster manager with the process that runs the query steps. YARN starts each executor on a core node with enough free memory and runs no step of the query; the cores per executor are a Spark setting. The query's steps run in the executors, and the driver plans them.

From code to a physical plan

Self-check: what does an Exchange do?

In the measured run of the June 2012 query on the 2 core nodes, stage 1 reads the 36 monthly files and computes partial totals, and stage 2 finishes the count and average per payment type. An Exchange (shuffle) separates the two stages. These are the measurements around the Exchange:

stage 1, scan       52 tasks on core nodes 1 and 2;
                    1 task, on node 1, had June 2012 trips
partial rows        5 from that task, one per payment type, 367 B in all
stage 2, planned    1000 shuffle partitions (EMR's default)
stage 2, ran        1 task, on core node 2:
                    adaptive execution merged the 1000 into 1
result              5 rows, to the driver
--- shuffle_answers: true --- ## In the June 2012 run, what moves over the network in the `Exchange` (shuffle)? 1. [ ] Input files, read again from S3 > Picking the input files treats the `Exchange` as a second scan. Stage 2 reads what stage 1 wrote, here 5 partial rows; the input files are read once, by stage 1. 1. [ ] Every June 2012 trip the scan kept > Picking every trip skips the partial totals. Stage 1 already added up its June 2012 trips into one row per payment type, so only those 5 rows go into the `Exchange`. 1. [x] Rows for a task on another node > The task on node 1 wrote 5 rows for the stage-2 task on node 2, so those 367 B went over the network. If the stage-2 task had run on node 1, those rows would not have crossed the network. ## In the June 2012 run, when could the stage-2 task start? \* 1. [ ] As soon as the task with the June 2012 trips had written its 5 rows > Starting stage 2 after the one task with June 2012 trips assumes Spark knows where the rows are. Spark cannot know that the other 51 tasks will add nothing until they finish, so every task of stage 1 must end first. 1. [x] Once the last of the 52 stage-1 tasks had finished > Stage 2 needs the partial rows from all of stage 1, so the `Exchange` is a stage boundary: the one stage-2 task started after the last scan task finished, although only one of the 52 tasks had rows for it. 1. [ ] As soon as the driver had built the plan > Starting stage 2 when the driver builds the plan confuses building the plan with producing data. The driver builds the plan before tasks run, but stage 2 must wait until the stage-1 tasks produce their rows. ## Spark planned 1000 shuffle partitions for stage 2 of the June 2012 query. What decides which of them gets a row? 1. [ ] Node that wrote the row > Picking the node expects rows to stay where they were written. A row can go to a task on any node; here the rows from node 1 went to a task on node 2. 1. [x] Row's key, its payment type > All rows with the same payment type go to the same shuffle partition. The plan's `hashpartitioning(payment_type, …)` hashes the key to choose that partition, so one task can finish the payment type's totals. 1. [ ] Order in which rows were read > Assigning rows by read order would split one payment type across several tasks. Rows with the same key must go to the same shuffle partition regardless of read order. ## In the June 2012 run, where were the 5 partial rows stored between stage 1 and stage 2? 1. [x] On node 1's disk > The stage-1 task on node 1 wrote its 5 rows to a shuffle file on node 1's disk, and the stage-2 task on node 2 fetched them from there over the network. 1. [ ] In S3, next to the input files > Picking S3 treats the `Exchange` as a write to storage outside the cluster. S3 holds the query's input files, which stage 1 reads once; rows between stages stay on the nodes' disks. 1. [ ] In the driver's memory > Picking the driver assumes the driver receives and passes on the partial rows. The driver plans the stages and receives only the 5 result rows from `collect()`; the stage-2 task fetched the partial rows from node 1 directly.

Running the plan: stages, tasks and waves

Which part of the run explains the wait?

The rides and average total per payment type for June 2012 ran over the 36 monthly files of taxi trips, about 520 million trips, on an EMR cluster with 2 core nodes (8 slots). The parts of the run, in order:

Part of the run What happened Time
Stage 1, scan: read, keep the June 2012 trips, partial totals 52 tasks, 36 of them read rows; a typical task took 1.65 s (9 in 10 took 1.75 s or less) 8.58 s
Exchange: partial rows to stage 2 5 rows, 367 B, written by 1 task; stage 2 waited 0 ms to fetch them (9 in 10 runs: 1 ms or less) none of its own: writing is in stage 1, fetching in stage 2
Stage 2, group totals 1 task 0.011 s
Whole query 8.90 s

Each time is the median over 50 runs of the query (5 runs on each of 10 clusters).

--- shuffle_answers: true --- ## A teammate wants to shorten the June 2012 query and starts with the group-by, because it is the one step that needs rows from other nodes. Which part of the run should a change target first? 1. [ ] Stage 2: group totals > Picking stage 2 assumes the group-by takes most of the time. Stage 2 ran one task for 0.011 s, because it added up only 5 partial rows. 1. [ ] `Exchange` between the stages > Picking the `Exchange` expects moving data between nodes to cost most. The `Exchange` received 5 rows, 367 B, and stage 2 waited 0 ms to fetch them. 1. [x] Stage 1: scan > Stage 1 took 8.58 s of the 8.90 s query, and stage 2 took 0.011 s: reading the 36 files took most of the time. The stage's *Duration* field shows the 8.58 s.

What sets the time of stage 1?

Stage 1 of the June 2012 query reads the 36 monthly files of taxi trips, keeps the June 2012 trips and computes partial totals. Stage 1 uses 2 core nodes, each with one executor of 4 cores; each executor core is a slot, which runs one task at a time. Spark cut the files into 52 Spark partitions, one task each:

tasks that read rows     36, about 1.65 s each (9 in 10 at 1.75 s or less)
tasks that read nothing  16, under 0.1 s each
slots                    2 executors × 4 cores = 8
stage time               8.58 s

The tasks that run at the same time, one per slot, form a wave (a term from Hadoop). The Spark UI’s event timeline shows each wave as a column of task bars; the UI does not use the term wave.

--- shuffle_answers: true --- ## Each slot runs one task at a time. What sets how long stage 1 takes on the 8 slots? 1. [ ] Total work split evenly over 8 slots > Dividing the total work by 8 assumes the work can be split evenly: 36 × 1.65 s ÷ 8 is about 7.4 s. Each task runs as a whole in one slot, so the 36 tasks cannot be spread evenly over 8 slots. 1. [ ] Slowest single task > The slowest task sets the stage time only when one task is much slower than the rest. Here each reading task takes about 1.65 s, and the 8.58 s stage time is about five task times one after another. 1. [x] Number of waves of tasks > The 36 tasks that read rows run in 4 waves of 8 and a fifth wave of 4, while the 16 empty tasks run in the other 4 slots, which are then idle: 5 waves of about 1.65 s is about 8.25 s, close to the 8.58 s measured. The 16 tasks that read nothing add only milliseconds.

What can make queries slow

Rows or totals into the Exchange?

From here on the lecture uses only the June 2012 trips, 15,096,468 of them (15.1 M), and steps run on 2 core nodes (8 slots):

trips       the June 2012 trips: 1 Parquet file, 8 row groups,
            read by 8 tasks; not bucketed
zones       the 265-row taxi zone table
broadcast   Spark automatically copies a table to every executor
            when it estimates the table at 10 MiB or less
--- shuffle_answers: true --- ## For each step on the June 2012 trips, what goes into an `Exchange` (shuffle)? Each option may be used once, more than once, or not at all. - count and average per payment type: `groupBy().agg()` :: partial totals > Each task totals its own rows first and sends one row per payment type it saw, a count and a sum, for the final stage to add up. The 8 reading tasks send 40 rows for the 15.1 M trips. - number of trips per pickup day: `groupBy().count()` :: partial totals > Each task totals its own rows first and sends one row per pickup day it saw, a count (a sum of ones), for the final stage to add up: at most 30 rows per task, one for each day of June. - each trip gets its payment type's average next to it: a window query :: every row > Every row goes into the `Exchange`, because no task can compute partial totals first: Spark puts the payment type's average next to every trip. All 15,096,468 trips, 86.5 MB, went into the `Exchange`. - join the trips to another large table, over 10 MiB :: every row > Every row goes into the `Exchange`: neither table is small enough for Spark to copy, so both send their rows by the join key. With broadcast turned off, the trips joined to the zone table sent all 15.1 M trips, 88 MB. - join the trips to the 265-row zone table: `F.broadcast(zones)` :: no shuffle `Exchange` > No trip rows move between Spark partitions: each task matches the rows in its own Spark partition against the copied 265-row table. The plan's `BroadcastExchange` copies the 265-row zone table to every executor, while a shuffle `Exchange` would repartition the trips by key. - keep only the trips for the first week of June 2012 and calculate two new columns from values in each row :: no shuffle `Exchange` > No trip rows move between Spark partitions: each task filters its own rows and computes the two columns within its own Spark partition. - :: one average per task > With one average per payment type from each task, the final stage could only average the averages, which is wrong when the tasks hold different numbers of trips (L5). A task sends a count and a sum instead, which the final stage adds up and divides.

Checks for a slow stage

Which change fixes a hot key, and which a spill?

A later query joins the June 2012 trips to the 5-row payment-type names table, a CSV file, with Spark’s automatic broadcast turned off. The query runs on 2 core nodes (8 slots) and takes 1.65 s. The Spark UI’s stage page shows these measurements for the stage after the Exchange (shuffle):

tasks             3; adaptive execution merged payment types 4 and 5
                  into the other two
records           7.8 million in one task, the trips paid by cash;
                  7.2 million in one, paid by card;
                  about 36,000 in the third, payment type 3
other slots       idle while the two large tasks run
--- shuffle_answers: true --- ## Cash and card are hot keys because millions of rows with each key go to one task. Which change shortens the query the most? 1. [x] Broadcast the names table > Copying the names table to every executor keeps the trips out of the `Exchange` and in their Spark partitions, so each task joins its own rows. With automatic broadcast off, `F.broadcast(names)` tells Spark to copy the names table. On the same cluster the query took 0.71 s with the broadcast and 1.65 s without; case P2.2 lists broadcast first, adaptive execution second and a salt third. 1. [ ] Give each task more memory > Picking more memory assumes the two long tasks spilled. Adding memory does not move rows: all cash trips still go to one task, which still processes all 7.8 million of them. 1. [ ] Run the join on the salted copy of the trips (the June 2012 trips written as several files in each payment-type folder partition) > Several files per payment type let more tasks share the scan, but the salted copy has no salt column: the salt was dropped before the write. The join still sends every cash row to one task by payment type, however many shuffle partitions or nodes there are. To split a hot key in a join, a salt is added to both tables when the join runs (case P2.2).

Another query sorts the June 2012 trips by pickup time, on the same cluster but with each executor given 1 GiB of memory. A spill occurs when a task’s share of executor memory is too small, so the task writes intermediate data to the node’s disk. The stage after the Exchange shows these measurements:

shuffle partitions  8, set with spark.sql.shuffle.partitions
tasks             8
task duration     median 2.4 s, longest 2.6 s
records           about 1.9 million in every task
Spill (disk)      about 150 MB in every task
GC time           about 0.8 s in every task
--- shuffle_answers: true --- ## Every task spilled, and the tasks are of even size, so the cause is memory per task. Which change helps? 1. [ ] Fewer shuffle partitions, so fewer tasks compete for memory > Fewer shuffle partitions put more rows in each task. With 4 instead of 8, each task holds twice the rows and gets at most twice the memory, so each task still has too little memory, and 4 of the 8 slots are idle. 1. [ ] Write the input with more row groups > Row groups change the scan, not the stage after the `Exchange`. File sizes and slots set the number of scan tasks, and row groups decide how many scan tasks find rows. The number of shuffle partitions sets the rows per task after the `Exchange`. 1. [x] More shuffle partitions, so each task holds fewer rows > More shuffle partitions reduce the rows per task after the `Exchange`. With 16 shuffle partitions, the stage runs 16 tasks of about 0.95 million rows, each needing half as much memory; giving each task more memory also works (Problem 4). More shuffle partitions help here because the tasks are of even size; rows with one key still go to one task, so more shuffle partitions do not split a hot key.

Terms used on this page

From the course flashcards, grouped by topic. Practise them in quiz mode, or try the match game.

Spark: shuffles and slow stages

Narrow transformation. A step each task does on its own partition, so no rows move between partitions: filter, select, withColumn.

Wide transformation. A step that needs rows from other partitions, such as groupBy, orderBy, a window or most joins. Spark adds a shuffle before it.

Shuffle (Exchange). Moving rows between partitions for the next stage: each task writes its rows to its node’s disk, and the next stage’s tasks read them, often from other nodes.

Window query. A step that computes a value over a group of rows and puts it on each row, such as each trip’s payment-type average next to the trip. Every row goes into an Exchange.

Hot key. One join, window or sort value with far more rows than the others. All its rows go to one task, which runs long after the rest of its stage; more nodes do not help.

Spill. Writing to the node’s disk when the rows a task sorts, groups or shuffles do not fit in its share of executor memory. The result is correct but slower.

Spark: how a job runs

Driver. The program that coordinates a Spark application: it runs your code, builds the query plan and sends tasks to the executors.

Executor. A Spark program running on an EMR core or task node. It runs tasks and keeps their data in its memory or on the node’s disk.

Partition. A chunk of rows that one task processes as one unit. When reading files it holds one or more splits, each a byte range of one file, planned from the file sizes and the number of slots.

Task. One stage’s work on one chunk of rows, run in one slot: by default, one executor core.

Slot. One executor core, as room to run one task on one Spark partition at a time. An executor with 4 cores runs 4 tasks at once; our EMR nodes have one per vCPU.

Stage. A set of tasks Spark can run before rows have to move between partitions. Every task in it runs the same steps on a different partition.

Wave. The set of a stage’s tasks that run at the same time, one per slot. 36 reading tasks on 8 slots need 5 of them.

Transformation. A step such as filter or groupBy(...).count() that is only recorded in the plan. No task runs until an action asks for a result.

Action. On a Spark DataFrame, a call such as df.count(), df.collect() or df.write.parquet() that makes Spark run the plan built so far. Unlike pandas, where each step runs as soon as you call it.

EMR cluster

Amazon EMR. AWS’s managed service that launches a cluster of EC2 instances with Spark installed. You pay for the nodes from launch until you terminate the cluster.

Primary node. The one EMR instance that runs the cluster manager and the HDFS name service. It runs no executors.

Core node. An EMR instance that runs executors and stores HDFS data. A role an instance plays in the cluster, not a Spark slot.

Task node. An optional EMR instance that runs executors and stores no HDFS data, so it can be removed or bought as spot capacity without losing HDFS data.

Also used on this page

Parquet. A columnar file format. Rows are grouped into blocks that each store every column separately, and metadata at the end of the file says where each part is.

Row group. A horizontal block inside one Parquet file, holding one column chunk per column. Its size is set when the file is written, and a file can hold one or many.

Folder partition. A dataset layout with one named location per value of a column, such as day=2012-06-14/ (on S3, a prefix). A filter on that column skips the other locations without opening them.

Instance type. The size you pick when you launch an EC2 server: how many vCPUs and how much memory it has, how fast its network is, and whether it has its own local disk.
