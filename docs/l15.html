Who does what in one question?

--- shuffle_answers: true --- ## A library's chat app answers questions about its `loans` table, one row per loan. The app stores the library's loan rules as short paragraphs, gives the model two tools, `get_schema` and `query`, and runs SQL in DuckDB. A reader asks "How many loans came back late and owe a late fee?". The steps below are in the order they happen. For each step, choose who does it. Each option may be used once, more than once, or not at all. - Finds the loan rules that match the question (RAG) and adds them to the user message :: Our app > RAG is our app's responsibility: it finds the matching loan rules and adds them to the user message. - Issues a tool call to `get_schema` to ask for a table summary :: Model > Asking for a tool is the model's part: it returns a tool call and cannot run anything itself. - Runs the tool and sends the table summary back to the model :: Our app > Running the tool is our app's responsibility: it runs the function and sends back the table summary. - Writes `SELECT COUNT(*) FROM loans WHERE returned_at > borrowed_at + INTERVAL 21 DAY` :: Model > Writing the SQL is the model's part: it arrives as the argument of a `query` tool call. - Extracts only the first SQL statement and checks that the query is executable over the table :: Our app > Checking the SQL is our app's responsibility: our code cuts and validates it before DuckDB sees it. - Executes the SQL and returns the result to our app :: DuckDB > Executing the SQL is DuckDB's part: the model never touches the data. - Writes the final answer in words based on the result :: Model > Writing the answer is the model's part: it reads the result and replies in words.

Our app runs the steps the model cannot

Who What they do
Our app Accesses RAG; provides tools for the model; checks and cuts SQL (post-processing); sends every request with the history
LLM Reads requests; returns tool calls or text; cannot run anything on our side
DuckDB Executes SQL on our side; the model never touches the data (but sees it if we send it)

History is our app’s job. The model does not remember the conversation: our app resends the whole history with every request.

Which technique fits each situation?

--- shuffle_answers: true --- ## A library has a chat app over its `loans` table, one row per loan. The app has `get_schema` and `query` tools, runs SQL in DuckDB, and stores the library's loan rules as short paragraphs. Match each situation to the technique that addresses it. Not all options will be used. - Model does not know what "late" means at this library :: RAG > RAG adds the matching loan rules to the user message. - Model needs the table's columns before writing SQL :: Tool calling > The model asks for the schema with a `get_schema` tool call. - App needs the answer as `{"count": ...}` to draw a chart :: Structured output > Structured output requests the answer in a fixed shape that code can read. - App tells the model to answer only library questions :: System prompt > The system prompt tells the model what it is for, on every call. - After a prompt change, we want to know if answers got better or worse :: Eval > An eval scores answers on a fixed dataset, before and after the change. - Generated SQL sometimes has extra text after the query ends :: Post-processing > Post-processing in our code cuts the text after the SQL. - :: Larger model > A larger model still does not know this library's rules or its data.

Each technique has a different role in the app

Technique What it does
System prompt Describes the task: what the model is used for; outlines the interaction; sent with every call
Tool calling Lets the model ask our app for something only our app can get or do
RAG Adds matching local rules or text to the user message
Structured output Requests the model’s response in a fixed shape. The model may fail to produce the shape, and a correct shape is not a correct result
Post-processing App code fixes simple, predictable mistakes in the output
Eval Measures whether a change made answers better or worse on a fixed dataset, scored by deterministic rules or by AI as a judge

What does each step rely on?

--- shuffle_answers: true --- ## In the same library chat app (tools `get_schema` and `query`, SQL in DuckDB, loan rules as short paragraphs), what does each step rely on? Each option may be used once, more than once, or not at all. - Sends the system prompt with every call :: Our code > Our code can still be wrong, so we rely on it through tests. A deploy could drop the system prompt. - Uses only columns from the schema :: Model > Model output varies from call to call, so we check it with a validator. An invented column makes the query fail. - Passes only a single SELECT to DuckDB :: Our code > Our code can still be wrong, so we rely on it through tests. A validator bug could let a `DELETE` through. - Answers in one sentence :: Model > Model output varies from call to call, so we check it. A paragraph costs output tokens we pay for. - Calls `get_schema` before writing SQL :: Model > Model output varies from call to call, so we check it. The model could skip the call and guess the columns.

We rely on code and the model in different ways

Reliance Instrument of correctness Why
Our code Tests Code can still be wrong; a bug repeats on every call
The model Validators on every call Output varies from call to call

In the cloud, responsibility is split between you and the provider. Here I use the word rely. You may rely on the model for a step, but making sure it happens is still your responsibility.

Terms used on this page

System prompt. The instructions the app sends first, with role system.

User message. The person’s question, and anything we add to it, like RAG chunks.

Tool call. The LLM asking our app to run a tool, with arguments (the SQL).

Tool result. What our app sends back after running the tool, as a message with role tool.

Reply. The LLM’s final answer in words.

Output format. A JSON schema sent with the request (strict mode).

Structured output. A reply that the provider returns as JSON matching a schema we give.

Strict mode. A strict JSON schema: the provider restricts which tokens can be generated, so a finished reply matches the schema’s fields and types (constrained sampling).

RAG (retrieval-augmented generation). Before the call, find the documents that match the question and add them to the prompt.

Term-based retrieval. Score a chunk by the words it shares with the question.

Embedding-based retrieval. A neural network maps each chunk to a vector where texts with similar meaning land close together, and the score is how close the question’s vector is.

Hybrid search. Term-based and embedding-based retrieval combined, as production systems often do.

Eval (evaluation). An automated test of a model’s answers over many inputs.

Dataset (Inspect). Labelled samples, typically a table with input and target columns. The input is the prompt, the target is the ideal answer or grading guidance.

Solver (Inspect). Produces an answer for each sample. It can be a single model call or an agent using tools over many turns.

Scorer (Inspect). Evaluates the output, using text comparisons, model grading, or other custom schemes.

Guardrail. A check on what goes into or comes out of the model that blocks or changes a request.

Trace. The record of one question: each tool call, the SQL, the checks’ verdicts, tokens, price and time.
