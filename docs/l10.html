L10 review: lakes, lakehouses and query engines

If you need to look up a term, the relevant vocabulary is below.

Layers of a lakehouse

Which layer does each tool or format belong to?

In a lakehouse, your files stay in your own storage, and you pick a separate tool or format for each part that a cloud warehouse supplies as one service. Each tool or format below belongs to one of those parts.

--- shuffle_answers: true --- ## Put each tool or format on its layer of a lakehouse. Each option may be used once, more than once, or not at all. - Parquet :: Storage format > Parquet encodes the rows of one data file, column by column, with a footer. The table format (Iceberg) is the metadata above many such files. - Spark :: Query engine > Spark SQL plans the query and runs the plan. On EMR, a cluster manager (YARN) starts Spark's executors on the cluster's nodes; YARN runs under the engine and is not a layer of the lakehouse. - S3 :: Object storage > S3 stores data files and metadata files as objects; the table's metadata records which files form the table. - Iceberg :: Table format > Iceberg's metadata files list the data files in the table's current snapshot, with the schema and the snapshots. Parquet encodes the rows. - Trino :: Query engine > Trino plans the SQL query and runs the plan on its workers. A connector gives Trino access to one source, such as a catalog, so it is part of the engine, not a layer of the lakehouse. - Glue Data Catalog :: Catalog > The Glue Data Catalog lists tables and points each Iceberg table to its current metadata file. - :: Cluster manager > A cluster manager (YARN on EMR, L5) starts Spark's executors on the nodes. It runs under the engine and is not one of the lakehouse's parts. - :: Connector > In Trino a connector is how the engine reads one source, for example the Glue Data Catalog (L10). It belongs to the engine, not to a layer of its own.

What the lakehouse changes

Data lake, lakehouse, or both?

An online shop’s orders, kept two ways. In the data lake, the table is a folder of Parquet files in S3, one subfolder per day. In the lakehouse, the table is an Iceberg table in the Glue Data Catalog over those Parquet files, partitioned by the day of order_time. Athena reads both tables and changes the Iceberg table.

--- shuffle_answers: true --- ## Does each statement describe the data lake, the lakehouse, or both? Each option may be used once, more than once, or not at all. - The rows are stored as Parquet objects in an S3 bucket :: Both > Both keep Parquet files in S3. The difference is the table format and the catalog above them. - A query skips day folders only if its filter uses the folder partition column :: Data lake > In a data lake the engine can skip day folders only when the filter uses the folder partition column (P2). An Iceberg table's partition value is derived from the order time (Iceberg partitioning), so a filter on the order time skips other days. - A delete adds a small file that lists the removed rows, and the data file is not changed :: Lakehouse > Iceberg calls it a delete file, and Athena's `DELETE` on an Iceberg table writes one (P4). Readers skip the rows it lists, and the data file itself is not changed. A folder of Parquet files has no delete files: changing a row means writing a new copy of its file. - A query can read the table as it was last Friday :: Lakehouse > Iceberg keeps each snapshot until it is expired, and time travel reads an earlier one (P5). A folder has no snapshots, so nothing records which files formed the table last Friday. - A data file is not edited after it is written :: Both > In both, a Parquet file is never edited once written. The lakehouse adds delete files or new data files instead (P4). - A reader lists the folder and reads whatever files are there now :: Data lake > A folder has no table commit that makes all files of one write visible together, so a reader can see part of a write (P1). An Iceberg reader finds the data files through the current snapshot's manifests instead of listing the folder. - :: Neither > Every statement here describes the data lake, the lakehouse, or both of them.

Terms used on this page

Lake and lakehouse

Data lake. Raw files in object storage, read by engines that list the folders; a folder of files has no commit, no record of its schema and no history.

Lakehouse. A lake whose tables have a table format and a catalog, so readers see whole commits.

Query engine. Parses SQL, plans it and runs it: Spark SQL, Trino, DuckDB, Athena.

Catalog. Lists tables and points to each table’s current metadata file: the Glue Data Catalog.

Table format. Metadata files that say which data files are the table now, with the schema and the snapshots: Iceberg.

Object storage. Keeps files as objects in buckets: S3. Which files form a table is recorded in the metadata above it.

Storage format (file format). Encodes rows in one data file, with a footer: Parquet.

Iceberg’s levels

Catalog entry. The table’s name and the path of its current metadata file.

Metadata file. The schema, the partition spec (how files are grouped, for example by month) and the snapshots; each snapshot names a manifest list.

Manifest. Lists data files, each with its partition value, row count, and minimum and maximum per column.

Data file. A file that contains rows of a table: a Parquet file.

Commit. Writing new metadata files, then switching the catalog entry to the new one in one step; readers see the old snapshot or the new one, never half.

Snapshot. One version of the table: the data files that were the table after one commit.

What the table format fixes

Iceberg partitioning. The table is partitioned by a value Iceberg derives from a column, for example the month of pickup_datetime, and each data file’s partition value is kept in the manifests. Because the value is derived (hidden partitioning), a filter on the column itself skips files, with no folder partition column to name. Separately, the manifests keep each file’s minimum and maximum per column, which also let an engine skip files.

Delete file. A small file that lists which rows of a data file are deleted. Readers skip those rows, and the data file itself is not changed.

Compaction. Rewriting many small data files into fewer larger ones (OPTIMIZE).

Time travel. Reading the table as it was at an earlier snapshot, as long as that snapshot has not been expired.

Not layers of a lakehouse

Cluster manager. Starts an engine’s processes on a cluster’s nodes, for example YARN starting Spark’s executors on EMR (L5).

Connector. In Trino, how the engine reads one source, such as the Glue Data Catalog or a database (L10).

_SUCCESS file. An empty file Spark writes when a job finishes writing a folder; readers of the folder do not check it by default.

Folder partition column. A column whose value is a folder name, such as month=2024-03; a data lake skips folders only when a query names it.
